# RocketWright：途中出力・最終出力の設計案

更新日：2026-11-04。仕様検討用の初稿。ここで提案する出力・確認工程・保存機能を実装済みと扱わない。

UI追補：2026-11-05。[UI・UX改訂案](ux-spec.md)で共通の配置、状態、比較・変更・組立の操作を具体化した。今回の画像改訂はコード側の対応状況を再調査した記録ではない。

## 1. 今回の前提

ユーザーの最新の指定を次のように反映する。

- 利用者はロケットの専門知識がない一般ユーザー。目的を対話で伝え、条件を確認する。
- 最初の対象は、**実際に打ち上げるペットボトル水ロケット**。展示用模型の作成を目的にしない。
- 節目ごとに途中成果物を確認し、ユーザーが次の工程へ進むか選ぶ。
- 黒いワークベンチと小さな整備員の表現を使う。作業員の形・大きさなどの細部は提案段階。
- 最終成果物には、設計・部品・製作データに加えて、設計解説動画と打ち上げCGを含めたい。
- 長期目標には、月へ向かうロケットとミッションの設計を含める。
- 詳細な組立方法を出力し、手・指・工具の作業余裕と順序を設計時に評価する。成人と子ども＋成人の条件を選べるようにする。
- 使用できるプリンター・材料・工具等を設定メニューから選び、案件の構造化条件として扱う案を加える。

以下のゲート、ファイル形式、画面項目、既製品と製作品の分担、保存方式は実装に向けた提案。数値の例は実機の試験結果ではない。
以前の[画像ドラフト](ui-drafts.html)にある「展示用模型」という出力名は、この最新方針に合わせて改訂する対象とする。

## 2. 全体の流れと確認する節目

| 節目 | ユーザーへ渡すもの | ユーザーが選ぶ操作 | 次へ進む条件 |
| --- | --- | --- | --- |
| G0 目的と条件 | 要求一覧、単位、条件の出典、機材プロファイル、未入力事項 | 条件を確定する／修正する／保存して終了 | 必須条件と達成基準、使える機材と不足情報が明示されている |
| G1 機体構成 | 構成図、部品一覧、既製品・製作品の区別、概形、概算費用、組立方式と作業者条件 | 構成を選ぶ／部品を変更する／前へ戻る | 選択した構成、固定部品、組立の成立見込みが記録されている |
| G2 解析と比較 | 公称飛行、ばらつき解析、要求との比較、組立アクセス、使えない解析と不足情報、候補差分 | この案を採用する／再解析する／不足情報を追加する | 必須評価の適用・入力・結果が揃い基準を達成。未達は差戻し、未評価は判定保留 |
| G3 製作データ | 部品別の形状、寸法図、組立図、詳細手順、手・工具の作業余裕、材料・製作条件、検査項目、対象版のマニフェスト | 製作版を確定する／図面・組立方法を修正する／検討用として保存 | 必要な入力、形状・寸法・手順の整合、担当者条件に対する組立評価と確認記録が揃う |
| G4 実機の記録と照合 | 製作後の実測値、部品の実物情報、検査・試験記録、設計との差 | 実測を反映して再解析する／記録を確認する | 必要な確認ごとに実施・未実施・結果を記録する |
| G5 解説・CG・出力 | 同じ採用版の解説、飛行CG、要求した成果物の一覧、まとめ保存 | 再生／個別保存／まとめ保存／生成だけ再試行 | 各成果物が対象版と生成元を示し、個別に完了確認できる |

G3で製作用データを取り出し、実物を製作してからG4へ戻る。G4を終えないと製作用データを取り出せないという循環にはしない。
G5の動画生成はG3の設計確定後に独立して開始できる。実機の確認待ちでも設計解説・シミュレーションCGは作れるが、実測映像や実機検証済みという表示へ置き換えない。

各ゲートは `準備中 → 確認待ち → 確認済み`。問題がある場合は `差戻し`、上流条件が変わった場合は `再確認が必要`。
ユーザーの進行確認と技術評価の合否を別に記録する。必須条件を変える場合は要求の版を更新してG0で再確認し、未評価項目に確認ボタンを押しただけで合格へ変換しない。
確認待ちでは下流の新しい設計判断・製作確定処理を自動で進めない。同じ解析内の残り試行や、ゲートで列挙した確認資料の生成は継続できる。
「次へ」の前に、確定する版・条件・未完了事項・次に実行する工程を一画面で示す。

## 3. 途中画面の常設情報

左に工程と構成、中央に対象の機体・部位、右に対話と確認事項を置く。進捗の文字情報は中央下部の同じ場所に置く。

| 項目 | 具体的に表示する内容 | 表示規則 |
| --- | --- | --- |
| 現在の仕事 | 風を変えて回収範囲を確認中、機体図を作成中など | ツール名の直書きを避け、実際に開始した仕事を示す |
| 対象 | 案A / v03、回収装置、フィン、機体全体など | 部位単位の処理と分からない場合は機体全体とする |
| 目的 | 何を確かめ、どの条件と比較するか | 一文と、必要なら評価項目へのリンク |
| 進み具合 | 完了件数 / 予定件数、実行中、待機中 | 完了結果を受け取った件数。予定総数が未定なら割合を出さない |
| 経過時間 | 実際の処理開始からの時間 | 待ち時間・実行時間・ユーザー確認待ちを区別する |
| 残り時間 | この工程の残り時間の範囲、または見積もり中 | 全探索の残り時間と混同しない。推定の対象と更新時刻を保持 |
| 直近の結果 | 途中の速度断面が届いた、高度の判定が終わったなど | 計算途中か確定かを示して短く通知する |
| 次の節目 | 回収解析が終わると、候補比較の確認に進む | ユーザーの次の判断を予告する |

表示例：`案A / v03 ｜ 風と回収を確認中 ｜ 72 / 100条件 ｜ 経過1分12秒 ｜ この工程の残り約20〜40秒`。
この例の件数と時間はUI説明用で、現在の実測値ではない。

整備員は、解析対象を点検する、完了時に道具を片付ける、確認待ちに資料を持って待つなど、状態と対応する。
`動きを止める` は演出だけを止める。`解析を中断する` とは別の操作にする。失敗・切断・確認待ちで作業を進め続ける演出はしない。

### 解析結果を映す背面スクリーン

[追加の画像案](ui-drafts.html#backscreen)では、整備員の背後に大きなモニターを置く。機体と作業員は手前にまとめ、後流の立体表示、速度断面、グラフを隠さない。右は途中結果の履歴に切り替え、対話へ戻る操作を別途用意する。

- 途中の画像・数値が届いた時点で結果を追加する。表示用に計算結果を生成・補完せず、解析器が出力した描画・データを使う。スカラー画像だけを受け取った場合、自由に回せる3D表示として扱わない。
- 各結果にジョブ、対象案・設計版、解析条件、結果ID、反復または物理時刻、生成時刻、到着時刻を持たせる。異なる版は同じ最新結果へ混ぜず、到着順が逆でも計算上の順序を保持する。複数の図の更新時点が違う場合は図ごとに示す。
- `最新に追従` が有効なら、到着した新しい結果を表示する。`この結果を固定` または履歴を選ぶ操作で追従を止め、固定中にも新着件数は知らせる。明示的に追従を再開するまで閲覧中の結果を切り替えない。
- 図には物理量、単位、凡例、表示範囲、必要な断面位置・等値面の定義を付ける。時点比較ではカラースケールを揃え、変更した場合は分かるようにする。格子依存性、残差、抗力の推移は別の図として扱う。
- 未収束・集計途中・確定・失敗を区別する。残差の低下だけで要求達成や空力モデルの妥当性を確定しない。反復数 / 反復上限を全体の完了率へ変換せず、曲線は実際に得られた反復まで表示する。
- 画像待ち、解析失敗、通信切断では最後に受け取った結果と更新時点を残し、現在も更新されている演出を続けない。結果が一件もなければ受信待ちを表示する。
- 整備員の演出停止、結果への追従、解析の中断を別々に操作できるようにする。図の拡大と説明・表による確認も用意する。画像更新はスナップショットで行い、点滅で通知しない。

この画像は構図と状態表示の案で、ユーザー提供の流体解析写真を参考にしたもの。写真の計算条件・数値の検証や、別チャットの解析処理との接続は行っていない。画像配信・履歴・実データ表示は実装対象として残る。

### 残り時間の計算案

- 同じ工程種別・規模・実行環境・計算設定で得た処理実績を使う。表示のために時間を作らない。
- 件数が決まる処理では完了件数と処理速度から幅を持って推定し、並列数や重い試行の影響を反映する。
- LLMの設計探索や追加試行の数が決まらない場合、工程名と経過時間を示し、全体の完了率は算出しない。
- ユーザー確認待ちは処理の残り時間から外す。資源待ちは待機時間として表示する。
- レンダリングでは完了したフレームを数え、後処理・音声・エンコードは別工程として示す。
- 実績が足りない、条件が変わった、通信が切れた場合は推定を無効化する。上限を超えても0秒で停滞させない。
- 更新頻度と計測件数の具体値は、実際に計測して決める。

## 4. 節目で受け取る途中成果物

| 成果物 | 最低限含む項目 | 更新する時点 | 途中でできること |
| --- | --- | --- | --- |
| 要求票 | 目標高度と許容範囲、積載物・質量、回収要求、予算、利用環境、固定部品、不明事項 | 条件を解釈・修正した時 | 確定、修正、途中版保存 |
| 構成案 | 部品ID、機能、取付相手、既製品／製作品、概形、採用理由、未確定寸法 | 構成候補ができた時 | 別案比較、部品変更、G1確認 |
| 部品別設計票 | 寸法・材質・質量、荷重条件、接続部、製作方法、根拠、検証状況 | 部品の版が作られた時 | 詳細閲覧、差戻し、変更依頼 |
| 解析結果 | 対象版、環境、解析手法、適用範囲、数値と単位、要求の閾値、合否、出典、制約 | 一つの解析が完了した時 | 図・数値の確認、候補比較、途中報告保存 |
| ばらつき結果 | 設定した変動条件、完了数と予定数、成功数、失敗理由、分布、乱数シード | 試行の完了に伴って更新 | 途中集計の確認。完了まで集計途中と表示 |
| 変更記録 | 変更前・変更後、変更理由、期待した効果、実際の評価、影響する結果 | 変更後の評価が完了した時 | 版の比較、差戻し、過去案を複製して検討 |
| 組立計画・作業余裕 | 工程順、対象者、両手・工具・治具、進入・操作・離脱経路、干渉、実物で確認する項目 | 組立方式・形状・作業条件が更新された時 | 条件切替、工程再生、困難箇所の確認、設計変更 |
| レビュー票 | 観点、対象版、根拠、指摘、重大度、担当、対応状況 | レビューを受け取った時 | 回答、設計修正、確認待ち |
| 確認パッケージ | 今回の成果、未解決、固定される条件、次に実行する内容 | G0〜G3の確認待ちに入る時 | 次へ、修正、保存して終了 |

不合格案も履歴に残し、理由と改善の経緯を見られるようにする。途中版の保存を、最終採用や製作承認として扱わない。
推定や根拠の説明は、使った値・出典・比較・変更理由の要約として出す。未検証の推測を数値結果として出さない。

### 結果一件の表示単位

`対象案と版 → 解析名と対象部位 → 何を確かめたか → 結果と単位 → 要求の基準 → 判定 → 条件・出典 → 次の操作`。

例えば到達高度だけを大きく出さず、要求範囲、飛行条件、公称飛行か多数回試行か、現在版の結果かを一緒に示す。
成功率には成功の定義、成功件数 / 有効試行数、予定件数、変動条件を添える。未実行は0%でなく `未評価`。
計算不能な試行を分母から無言で除外しない。有効・無効の件数と集計規則を示し、規則が未確定なら全体判定は `判定保留` とする。

## 5. 水ロケットで規定する要求と評価

| 分類 | 入力として確定するもの | 途中・最終で出すもの |
| --- | --- | --- |
| ミッション | 目標高度、許容範囲、積載物、質量、回収の意味、予算 | 要求達成表。到達・着地・積載物の状態を別項目で判定 |
| 使用条件 | 発射場所の環境、風の想定、使用機材、許容される運用条件の根拠 | 各解析で使った条件、変動幅、確認先、未確定の項目 |
| 圧力を保持する既製品 | 使用するボトル、ノズル、ランチャー、適合関係、製品資料 | 型番・仕様・資料・点検記録。初期案では独自の耐圧部品を自動設計する範囲に含めない |
| 外形・取付部品 | ノーズ、フィン、支持部、積載物保持部、回収装置の取付構成 | 部品別の寸法、材質、質量、接続条件と製作対象の区分 |
| 飛行 | 質量、外形、空力・推進モデル、環境、数値計算条件 | 高度・速度・時間・軌跡、使ったモデルと簡易化、要求との比較 |
| 姿勢と安定性 | 必要な形状・質量分布・適用可能なモデル | 重心・圧力中心・安定性の評価。モデルが無ければ未評価とし、飛行成功だけから安定としない |
| 回収と積載物 | 開傘の想定、接続、降下、衝撃、積載物への許容条件 | 解析できたものと実機で確認するもの。低い降下速度だけで卵の無損傷を実証済みにしない |
| 製作・実物 | 材料、寸法、製作方法、取り付け、実測質量・重心、試験条件 | 設計値と実測の比較、再解析が必要な差、部品・試験ごとの記録 |

JAXAの[ソラトビ手帳2026](https://edu.jaxa.jp/contents/soratobi/assets/ST2026.pdf)に示される既製の炭酸飲料用ボトルと市販ノズルの構成を、初期の製品範囲を考える参考にする。形状や条件を全機体に適用する規格として流用しない。
材料の適否、許容条件、取り付けや回収の成立を、メッシュが出力できたという理由だけで確認済みにしない。

## 6. 部品票と実機用の製作データ

最終出力では、機体全体の一体メッシュだけでなく、製作する部品と購入する部品を分ける。

| 部品票の項目 | 記録する内容 |
| --- | --- |
| 識別 | 部品ID、部品名、部品版、属する機体版、左右・向き・個数 |
| 役割 | 機能、接続相手、要求ID、必要な荷重・環境条件 |
| 調達区分 | 既製品、切り出し・加工品、3Dプリント品、消耗品 |
| 既製品 | 製造者、型番、仕様・寸法、適合機材、資料のURLと確認日、代替可否 |
| 幾何 | 基準面、座標系、単位、重要寸法、相手部品との位置関係、公差とその根拠 |
| 材料 | 材料名とグレード、材料データの出典、適用条件、未確認事項 |
| 質量 | 設計上の推定値、推定方法、実測値、重心への寄与。積載質量・乾燥質量・発射時質量を区別 |
| 製作条件 | 製作方法、対象機材、必要な設定、仕上げ・組立条件、確認した工程版 |
| 組立性 | 工程ID、作業者条件、手と工具、保持方法、作業経路、余裕、公差、必要な実物試行 |
| 検証 | 形状検査、寸法検査、取付・機能の確認、必要な試験、結果の資料、確認者・時刻 |
| 変更影響 | 変更で無効になる解析・図面・相手部品・動画、改訂理由 |

プリント出力の対象は、選択した製作方法で成立性を確認する外形・保持・取付部品など。圧力容器・耐圧ノズル・発射機材の新規設計へ自動で範囲を広げない。
プリント条件は材料・機材・必要な性能に結び付けて記録する。共通の積層条件や充填率を根拠なく全品へ割り当てない。
機材や材料が決まっていない段階では、形状の検討用出力とし、製作条件を確定済みと表示しない。
必要な試作や寸法・取付の確認は、検討用の部品出力を使って行い、結果を同じ製作レビューへ戻す。初回の形状を出すために実物の完成を先に要求する循環にはしない。

製作データの提案：編集可能な寸法・パラメータを正とし、形状データと図面を同じ版から派生させる。3MFを主なプリント交換形式、STLを互換出力候補とする。
実寸1:1、記録単位mm、部品のローカル座標と組立時の位置を明示する。部品数、向き、合わせ面、取付寸法、体積と質量の整合を検査する。
出力形式・拡張の適合と実機への適用確認は別の記録にする。3MFの形式選定には[3MF Consortiumの仕様](https://3mf.io/spec/)を参照し、実際に使う版と受け側アプリの対応を固定する。
プリンター・材料・工程が未確定ならG-codeは生成しない。表示用GLBだけを製作用の正データにしない。

### 使用できる機材を選ぶ設定

[機材設定の詳細仕様](equipment-settings-spec.md)では、上部右の設定からプリンター・材料・工具・作業者等を選び、標準設定と案件用スナップショットを分ける案を定義する。
選択した機材ID・版と構造化した制約を設計・製作・組立へ渡し、同じ機材情報を対話で繰り返し抽出する工程を減らす。処理量の削減率は未計測。
不足情報を持つ設定も下書き保存できるが、製作版の確認済みにはしない。案件への適用時に、影響する部品・手順・結果を再確認する。

### 組立方法と手・工具の作業余裕

[組立性の詳細仕様](assembly-spec.md)と[例示データ](assembly-contract.examples.json)で、成人と子ども＋成人のプロファイル、工程順、両手と治具、進入・操作・離脱、視認、部品公差、実物試行を定義する。
指が入ること、操作中に手・工具が動くこと、実物で作業が成立することをそれぞれ確認する。小さな整備員は工程の案内役とし、評価では対象条件に基づく実寸の手と工具を表示する。
一律の指幅・余裕や、根拠のない締結・接着条件を生成しない。未解決の組立アクセスはG3の確認事項として設計へ戻す。

図面PDFは概要用と部品製作用を区別する。ページ数や尺を固定の品質基準にせず、その機体で必要な内容を揃える。
未生成のものはダウンロードリンクを作らず `未生成`、処理中は `生成中`、失敗は理由と再試行、古い版は `旧版` とする。

### 最終画面の情報順

1. 採用案と版、目的、確定した範囲、要求達成と未検証。
2. 機体・部品・設計図を確認する表示。
3. 製作する部品と、購入する部品。
4. 根拠になる解析と実機の記録。
5. 解説・CG動画の再生と生成状況。
6. 個別保存とまとめ保存。

「解析条件を達成」「製作版を確定」「実機確認の記録あり」「動画生成完了」は別の状態として表示する。
数値解析が合格したという表示から、機体が実機で検証済みという結論へ自動で進めない。

## 8. 動画で説明する内容

### 設計解説

- 目的と要求：何をどの条件で達成する機体か。
- 全体構成：ボトル、ノーズ、フィン、積載物保持、回収装置など、実際の部品IDに対応する形。
- 部位の役割と選定：採用理由、比較した案、寸法や材質の根拠、変更で何が改善されたか。
- 解析：入力した環境、公称飛行と変動の区別、結果、達成・未達・未評価。
- 製作と確認：購入するもの、製作するもの、実測で確認する項目、対応する図面への案内。

全体を短く見るプレビューと、部位ごとに見られる解説を別に用意する。既存の約10秒映像は表現と生成工程の参考で、全機体の解説尺を固定する根拠にしない。
ナレーションの有無と長さは未確定。まず字幕・部品ラベルだけでも必要な説明を追える構成にする。
説明文とHUDの数値は確定した設計・解析・根拠から参照する。未作成の内部構造や機能を、見た目のために発明して表示しない。

### 組立解説動画

組立手順の工程IDから、部品の向き、持ち方、挿入、操作、工具の取り外し、完了確認を示す。手・工具・治具は実際に評価する条件へ対応させる。
動画とPDFを同じ手順から生成し、対象者や工具の違いによる分岐を表示する。幾何アニメーションだけで必要な力や実物での成立を確認済みにしない。

### 打ち上げCG

発射前の全体、上昇、頂点、回収など、その機体の解析で扱える場面を選ぶ。水ロケットの噴射と外形を対象機体に合わせる。
時系列データに機体位置と時刻を対応させる。早送り・スロー再生は再生速度を示す。
現在のデータに無い機体姿勢、開傘の詳細、煙・水しぶき等を描く場合、実際に解析した運動と表示上の演出を生成記録で区別する。
説明用の映像が変わっても、確定した部品形状と解析値を勝手に変更しない。

動画ジョブは、モデル準備・台本／字幕・3D描画・合成／音声・書き出し・検査に分けて状態を持つ。
失敗した工程だけを再実行し、完成した設計データを巻き戻さない。設計変更後の動画は旧版にし、自動で最新版の映像として再利用しない。

## 9. 途中・最終を結ぶデータ管理

画面上は案A / v03のような読める名前を使い、内部では次を保持する。

| 識別・版 | 用途 |
| --- | --- |
| project_id / run_id | 同じプロジェクトの別の探索・再実行を区別 |
| requirement_revision / environment_revision | 要求と環境の変更を識別 |
| equipment_profile_id / equipment_revision | 案件で使用する機材・材料・工具・作業者条件のスナップショットを識別 |
| candidate_id / design_revision / design_fingerprint | 同じ案の改訂と、実際に評価した入力を照合 |
| part_id / part_revision | 部品と図面・部品票・取付相手を接続 |
| evaluation_id / source_id | 計算値を出した処理と根拠を接続 |
| gate_id / decision_id | ユーザーが何を確認し、どの版に対して進行を選んだか |
| job_id / artifact_id | 処理状態と、完成した一つのファイルを接続 |
| sequence / timestamps | イベントの順序、開始・更新・完了の時刻を識別 |

各結果は対象の設計・要求・環境・モデル・カタログ・評価基準の版に結び付ける。必要ならシード、試行数、計算設定も含む。
構造の具体例は[output-contract.examples.json](output-contract.examples.json)。各ケースは独立した説明用スナップショットで、現在のAPI形式や実機の評価結果ではない。
形状・条件が変わった場合は依存する結果と確認を無効にする。依存関係を説明できない解析は、初期実装では全体を再評価する。
再利用する結果は入力と処理条件の一致を確認する。後から届いた旧runの結果を、現在の表示へ混ぜない。
過去案は復元・複製して比較できるが、履歴を上書きしない。

途中保存は現在の入力、設計版、完了結果、実行中の範囲、確認記録をスナップショットとして保存する。
プロセスやブラウザーを閉じた後も再開できる仕様には永続保存が必要。途中の単一計算を再開できない場合は、その工程だけ再実行すると明示する。

## 10. ファイルの状態とまとめ保存

成果物の状態は `planned / queued / generating / ready / failed / cancelled / stale`。
通常の `ready` には対象版、生成元、実ファイルの保存先、ファイルサイズ、ハッシュ、完了時刻、必要な検査を含める。
レビューや入力不足で作れない場合は、理由を示して未生成のままにする。承認前の部品データには `検討用・未確定` を付ける。

提案するパッケージ例：

```text
rocketwright-design-a-r03/
  README.md
  manifest.json
  design/requirements.json
  design/environment.json
  design/equipment.json
  design/design.json
  parts/bom.csv
  parts/part-records.json
  models/display.glb
  manufacturing/parts/                 # 確定した対象部品の3MF / STL等
  manufacturing/process-records.json
  assembly/instructions.pdf
  assembly/steps.json
  assembly/operator-profiles.json
  assembly/access-evaluations.json
  assembly/verification-records.json
  assembly/figures/
  drawings/assembly.pdf
  drawings/parts/                      # 部品別PDF / SVG
  analysis/results.json
  analysis/flight-trace.csv
  analysis/dispersion.json
  analysis/reviews.json
  history/design-decisions.json
  hardware/measurement-records.json
  hardware/test-records.json
  videos/design-explanation.mp4
  videos/launch-cg.mp4
  videos/assembly-guide.mp4
  videos/subtitles.ja.vtt
  provenance/sources.json
  verification/checks.json
```

このツリーは設計案。要求され、生成できた成果物だけを格納する。中身の無いダミーファイルを完成物として入れない。
目録には、要求したが未完了・失敗・未評価の項目も状態と理由を残す。
`設計データを保存（動画なし）` と `動画も含めて保存` を分け、動画を待たずに完成した設計データを取り出せるようにする。
まとめ保存の対象版は固定する。保存中の新しい結果を無言で混ぜない。

外部へ渡す成果物は、単位・改訂・出典・必要な利用表示を保つ。不要な作業名、個人環境の絶対パス、認証情報、一時URLは格納しない。
提出・公開を行う際のチェックは、実際の対象ファイル・URLを決めた時点で別途実施する。この仕様作成だけで最終提出チェック完了とはしない。

## 11. 異常時・変更時の動作

| 状況 | 見せるもの | 操作・保存の扱い |
| --- | --- | --- |
| 目標を満たす案がない | 条件未達、最も近い案、不足の理由と根拠 | 条件修正、追加探索、検討結果の保存。合格と表示しない |
| 計算が成立しない | 対象、入力、適用範囲、失敗した処理 | 判定保留。失敗値でグラフや成功率を埋めない |
| レビューが利用できない | 未実施と、完了した観点 | レビュー成功に置き換えず、規定した必須確認は確認待ち |
| ユーザー確認待ち | 判断が必要な点、対象版、次の処理 | 完了結果を保持。下流の新しい確定処理は待機 |
| 中断 | 中断要求中と、停止を確認できた仕事 | 停止確認前に中断済みにしない。完了データは保持 |
| 切断 | 最後の受信時刻、保存済みの結果、状態を確認中 | 再接続して実状態と照合。切断を解析成功に変換しない |
| 条件・部品の変更 | 改訂差分と、影響して旧版になった結果 | 対象版を更新。必要な解析とゲートを再確認 |
| 動画・ファイルの生成失敗 | 失敗した成果物と理由、既に完成したもの | 完成物は保存可能。対象工程だけ再試行 |
| 未対応の機能 | その項目は未評価／未生成 | 不明なままの項目を含むことを報告。リンクや合格値を捏造しない |

## 12. 水ロケットから月への拡張

共通にするのは要求、階層構成、部品・サブシステムの版、解析根拠、ゲート、変更影響、成果物の目録。
`vehicle_scale` と `mission_profile` を分け、機体の規模と目的地を一つの列で代用しない。

| 段階 | 主な対象 | 追加して規定する出力 |
| --- | --- | --- |
| 初期 | 実機の水ロケット | 上記の部品・製作・飛行・回収と実機照合 |
| 次段階の候補 | 市販認定モーターを使う小型機 | モーター資料との対応、機体・回収・運用条件、適用モデルの検証 |
| 軌道投入 | 多段機と積載物 | 段構成、質量・性能配分、投入条件、飛行フェーズごとの検証、インターフェース |
| 長期 | 月へ向かう輸送ミッション | 地球周辺の出発条件、月への遷移、到着目標、質量・エネルギー配分、段・宇宙機の役割と各検証 |

月への到達・月周回・月着陸のどれを最初の目標にするかは未確定。実機設計を長期目標に持ちつつ、対応する物理・システム・製造・試験の能力を段階ごとに追加する。
現行の高度・地球軌道向けの解析が、そのまま月ミッションに対応しているとは扱わない。
将来の出力も `要求を満たす解析`、`製作可能性の確認`、`実機検証`、`運用に必要な判断` を区別する。
段階を進めながら要求・設計・実現・検証を接続する考え方の参考は[NASA Systems Engineering Handbook](https://www.nasa.gov/reference/systems-engineering-handbook/)。ここで定義したゲートは本サービス用の提案で、NASAの審査を行ったという意味ではない。

## 14. 仕様を実装へ渡すときの受け入れ例

1. 解析中の数値と図を開くと、対象案・版・条件・出典へ辿れる。
2. 72件完了のイベントで件数と作業対象が更新される。通信が止まっても進捗は勝手に増えない。
3. 途中集計で無効試行が発生すると件数と集計の扱いを確認でき、最終の成功率を誤って表示しない。
4. G1確認待ちでは部品構成をユーザーが選べる。選択記録なしに下流の製作版を確定しない。
5. v03の部品を変更してv04にすると、影響する結果と承認を旧版とし、遅れて届くv03のイベントを混ぜない。
6. 寸法・材料・製作方法に未入力がある部品は、製作用データが確認済みという表示にならない。
7. 図面の部品ID、部品票、部品表の数量、形状と単位が同じ対象版を参照する。
8. 設計値と実測値が違う場合、その差と再解析の必要性を確認できる。未試験を試験済みにしない。
9. 動画に出る形・部品・数値が採用版と一致し、設計変更で旧版となる。
10. 動画が失敗しても完成した設計データを保存できる。まとめ保存の中に未生成のダミーは入らない。
11. 動きを止めても、解析名・対象・件数・時間・失敗理由を読める。
12. 月ミッションを選んでも、未対応の計算を成功させた表示や架空の到達結果を作らない。
13. 子どもと成人を選んだ場合、片方の幾何チェックだけで全体の組立を確認済みにしない。
14. 完成位置では干渉しなくても、工具を入れる・回す・抜く途中の問題を示せる。
15. 手順変更やカバーの追加で内部に手が届かなくなる場合、該当する工程と結果を再評価する。
16. 詳細手順の寸法・条件・工具・確認基準を確定データへ結び付け、不明値を作らない。
17. 標準機材の更新で既存案件の入力を勝手に変更せず、案件用の版で条件を再現できる。
18. 機材未登録とプリンターを使わない指定を区別し、不明な寸法・材料を無制限や確認済みにしない。
