# デモの物語と技術の伝え方

短いデモは、対象者や体験を理解してもらい、動くものを見せ、その動作を成立させた工夫を伝える。以下は[大会の評価項目](01-events-and-judging.md)と運営者・参加者の助言を組み合わせた構成の提案。

## 一つの場面を入力から結果まで通す

主な利用者を一人、利用する場面を一つ選ぶ。実際の入力が処理され、意味のある結果に変わる流れを見せる。Devpostは、画面収録と説明でアプリの動きを分かるようにすることを勧める。Kesslerの寄稿も、背景を短く説明し、動作によって最初の問題がどう解かれるか見せるよう助言している。[Devpost](https://help.devpost.com/article/84-video-making-best-practices)、[寄稿](https://techcrunch.com/2014/09/01/how-to-crush-your-hackathon-demo/)

| 場面 | 見せること | 話すこと |
| --- | --- | --- |
| 利用前 | 現在の作業、困り事、遊びの従来の操作 | 誰がどこで何をしたいか |
| 入力 | ファイル、絵、操作、センサー等 | この入力が何を意味するか |
| 操作 | 価値を生む処理を起動する | 何が起きるかを短く予告する |
| 結果 | 生成物、状態の変化、反応、判断材料 | どこを見れば成功が分かるか |
| 意味 | 利用前と結果の比較 | 便利になったこと、面白さ、新しい可能性 |

結果が出た直後は、見る場所を示してから意味を説明する。「こちらが結果です」だけで進まず、入力との関係を短い言葉で指す。長い待ち時間や複数の枝分かれは、事前に扱い方を決める。

娯楽作品なら「誰が困っているか」を無理に作らず、どんな新しい体験や楽しさがあるかを示す。社会的影響を評価する大会では、そのテーマへの関係も説明する。すべての大会を同じ問題解決型の型へ押し込まない。[HackNTX](https://www.hackntx.com/judging-criteria)、[HerTechVenture](https://hackathonhertech.usal.es/reglamento)

## 操作のどこを省くか

アカウント作成、長い文字入力、設定画面の巡回など、作品の価値を示さない操作は事前に済ませる。必要な文は入力例として準備する。認証自体が作品の新規性なら、その動作は中心として見せる。[Kesslerの助言](https://techcrunch.com/2014/09/01/how-to-crush-your-hackathon-demo/)

省略した条件は隠さない。「テストアカウントで開始」「このファイルを入力に使用」「時間のかかる処理は事前実行」と示す。規則がライブ実演を求める場合は、事前実行や動画が代替として認められるか確認する。

## 技術説明を三段階にする

1. **全員に分かる動作:** 何を入れると、何が返るのかを画面で示す。
2. **技術者が評価できる難所:** どの制約があり、何を選んで解いたかを一つ説明する。
3. **質疑で確かめる詳細:** 実装箇所、計算、構成、ログ、既存ライブラリとの境界を補足へ置く。

二段階目は、次の形で話す。

> ［実現したい体験］には［制約］があります。単純に［方法A］では［問題］が残るため、［方法B］を選びました。その結果を［動作・比較・記録］で確認しました。

これは独自に作成した型。AshiArtの道路上の経路、4DX@HOMEの同期、mimocaの測位など、制約と実装を結び付けて記述する受賞例を参考にしている。[受賞事例](06-winner-patterns.md)

## 構成図とコードを見せる

構成図は、入力、自作の主要処理、外部サービス、保存・検証、出力など、デモを理解するために必要な部分へ絞る。矢印に何が流れるかを書き、自分たちの実装と既存の部品を区別する。デモと関係しないインフラまで一度に説明しない。

コードは、工夫を直接示せる短い箇所を選ぶ。エディター全体を小さく映すより、該当する処理と、そこから起きる動作を対応させる。高度な実装でも、コードを映すだけでは難しさを説明したことにならない。

HackNTXはコードの見た目や本番品質そのものを採点しないと明記する。一方、他大会では技術性や再現性が評価される。コードの美しさ、動作、技術難度、再現方法を同一の評価項目として扱わない。[HackNTX](https://www.hackntx.com/judging-criteria)、[Hack U](https://hacku.yahoo.co.jp/hacku2025_tokyo)

## 何を独自性として伝えるか

| 材料 | 伝わる説明へ変える問い |
| --- | --- |
| 新しいライブラリやAPIを使った | それによってどの体験が可能になったか |
| 複数の技術を組み合わせた | 組み合わせる際に何が難しかったか |
| 精度・速度を改善した | 何と、どの条件で比較したか |
| UIを工夫した | 利用者のどの操作や迷いを変えたか |
| ドメイン知識がある | その知識がどの制約・評価・判断を必要にしたか |
| チームで協力した | 誰が何を担当し、どの連携で動作を通したか |

苦労の長さは、技術的な価値の証明とは別である。「徹夜した」「実装量が多い」から一歩進め、解いた制約と確認できる結果を示す。

## APIやAIを使う作品

入力、呼び出す処理、外部APIの出力、自作部分の加工・検証、最終成果を分けて説明する。キャッシュ、録画、ダミーデータ、人の判断を使う場合は、その範囲も示す。

一般大会では、API名の露出よりも、そのAPIを使って何を作ったかを評価項目へ対応させる。スポンサー賞で特定製品の利用が条件なら、必要な利用が実装されていることを、提出物と動作で示す。[大会比較](01-events-and-judging.md)

RocketCreaterに適用するなら、「候補の生成→制約の判定→検証結果→制作物への反映」のうち、実際に通せる一つの流れを選ぶ。ドメイン知識がどの制約や評価を必要にしたかを説明する。これは発表設計の案であり、現時点の実装や検証結果を宣言するものではない。

## 提出ページと発表をつなぐ

短い発表で省いた情報は、指定された提出ページやREADMEへ整理する。目的、動作の入口、起動・再現方法、利用技術、担当、自作した範囲、既知の制約を確認できるようにする。公開範囲は大会の指定に従う。[HP SCDSの実行物と説明の要件](https://industriales.usal.es/2024/02/08/21348)、[Devpost](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)
