# ライブ実演と動画の作り方とトラブル対策

## 発表方式で準備を変える

| 方式 | 中心になる準備 | 当日に確認すること |
| --- | --- | --- |
| ステージでのライブ | 一つの流れ、操作担当、画面切替、短縮版 | 投影、音、ネット、操作に使うPC、持ち時間 |
| ブース巡回 | 短い説明とデモを何度も再開できる状態 | 審査員が到着した時点から見せられるか |
| 動画提出 | 台本、実際の画面と入力、説明、アップロード | 長さ、公開範囲、再生できるか、締切 |
| ハードウェア・複数端末 | 機器と画面を対応させる撮影・配置 | 電源、接続、反応の見え方、運搬後の復旧 |

MLHはブース巡回方式を推奨する。国民大学OSS研究室のマニュアルは、指定PC、映像・音声の利用、端末切替にかかる時間などを事前に告知・確認するよう記す。[MLH](https://guide.mlh.io/general-information/judging-and-submissions/judging-plan)、[韓国語の運営マニュアル](https://github.com/KMU-OSS-Laboratory/Hackathon-Manual/blob/master/manual.md)

## ライブで操作を止めない

- スライド、アプリ、結果を出す順番を決め、実際の共有画面で通す。
- 必要なテストアカウント、入力例、初期データを用意し、デモ後に同じ状態へ戻せるようにする。
- 主な説明者と操作担当を決める。交代が必要なら、合図と切替も計時する。
- 見る場所を言葉とカーソルで示す。動作を先取りして早口で説明し続けず、結果を見る時間を残す。
- APIキー、関係のない通知、個人データ等が共有画面へ出ないようにする。

これらは運営条件と参加者の失敗例を踏まえた準備案。かっぴー氏の体験では、ローカルで動作していてもZoomの操作が実演を妨げた。実装確認と発表環境の確認を両方行う。[参加記](https://note.com/kappy713/n/n0afb2b86c617)

## 動画を作る

Devpostは、画面収録と説明音声によってアプリの動きが分かる動画を勧める。冒頭で何をする作品かを伝え、実際に入力し、どう役立つかを示す。台本と録画の準備を早めに始め、再生とアップロードの時間も確保する。[公式ヘルプ](https://help.devpost.com/article/84-video-making-best-practices)、[参加者の助言集](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)

1. **台本と画面を対応させる。** 各文を話す時点で、何が映るか決める。
2. **価値が分かる流れを録る。** 設定から全画面を巡回せず、代表的な利用を通す。
3. **必要な部分を編集する。** 不要な入力や待ち時間を整理する。時間を省略・倍速にした場合は分かるようにする。
4. **音と文字を確認する。** 実際の再生サイズで、画面・字幕・数値を読めるか確認する。
5. **書き出して再確認する。** 最終ファイルの長さ、映像、音声、提出したURLからの再生を確認する。

編集は、実装していない反応や成功を作るために使わない。異なる実行の映像をつなぐ場合も、一回の連続実行に見せてよいか注意する。モック、事前計算、録画は表示や説明で区別する。

## 音声とBGMと字幕

Devpostの参加者の助言は、聞き取れるマイクと簡潔な説明を重視し、時間内へ詰めるために音声を速くしないよう勧める。[原文](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)

以下は編集上の提案。

- 説明音声を中心にし、BGMは理解の妨げにならない場合だけ使う。なくても成立する構成にする。
- 音を扱う作品は、その音自体が証拠になる。説明と作品の音を混ぜすぎず、何を聞けばよいか示す。
- 字幕は画面の操作部や結果を隠さない位置へ置く。専門語は一度説明し、字幕とUIで表記をそろえる。
- ハードウェアは機器の動作音だけに頼らず、近接映像や状態表示も用意する。
- 最終ファイルを小さめの画面や普段の再生環境でも確認し、聞き取りやすさを確かめる。

## 障害を想定して用意するもの

| 起きやすい問題 | 事前の準備 | 発表中の対応 |
| --- | --- | --- |
| 会場ネット・外部サービス不調 | 資料と実動作の録画をローカル保存 | 現在の状況を説明し、認められた記録へ切り替える |
| ログイン・権限・期限切れ | テスト利用者で再確認、必要な権限の準備 | 同じ認証操作を繰り返さず、用意した次の手段へ進む |
| APIの遅延や非決定的な出力 | 入力例、所要時間、失敗条件、実行済み記録 | 本番と事前実行を区別して示す。失敗を成功に見せない |
| 画面共有やウィンドウ切替の問題 | 発表モード・共有範囲・メニューを含む通し練習 | 操作担当が既定の画面へ戻す |
| PCやファイルの問題 | チームで動く版・資料・動画を共有 | 別環境に移れるかは運営条件に従う |
| ハードウェアの反応が見えない | カメラ、近接映像、結果の表示 | 機器と画面の関係を説明し、見える形の記録へ進む |
| 時間切れ | 短縮する操作と説明を決める | 主要な結果と実装範囲を優先して締める |

BreathVizAIの作者は、会場で通信が不安定になった際、ローカル保存された資料に助けられたと記す。韓国の参加記には、録画直前のPC不調もある。予備を用意する根拠は、抽象的な不安だけでなく実際の事例にもある。[BreathVizAI](https://zenn.dev/0_s0g0/articles/7918ca4a2bc3b8)、[共同ハッカソン参加記](https://velog.io/@dongvelop/해커톤후기)

## 復旧を何度も繰り返さない

ライブ実演、実際に動いた録画、画面と結果の記録という順に代替を用意し、どこで切り替えるか事前に決める。例えば数秒で復旧できないなら次の手段へ進む、という自分たちの判断基準を作る。これは大会共通の許可ではなく、使える代替手段は運営へ確認する。

未完成の時には、動作する部分、試したこと、未解決の点を正直に示す。HackNTXは未完成作品でも学びを共有することを勧める一方、技育展2026は予選までに動作する作品を求める。代替説明だけで参加条件を満たすかは大会によって異なる。[HackNTX](https://www.hackntx.com/judging-criteria)、[技育展2026](https://geek.supporterz.jp/geekten/2026/information)

## 提出前の再生確認

提出URLをログアウトした状態でも開き、アクセス権、処理の完了、音声、字幕、再生位置、長さを確認する。非公開・限定公開・公開の指定は大会に合わせる。リンクが発行されただけで処理と確認が終わったとは扱わない。Devpostも、非公開動画では審査員が閲覧できないことや、直前のアップロードを避けることを注意している。[Devpost](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)
