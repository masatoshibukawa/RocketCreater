# ハッカソンの時間別台本と質疑と練習

次の秒数は独自の構成案で、発表だけの持ち時間を前提にする。質問、接続、機器の切替が時間に含まれる場合は先に差し引く。短い枠でも動作を見せられるようにし、最後に実装の成果と範囲を残す。

## 1分で動作と強みを見せる

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:08 | 何をする作品か、誰にどんな体験を提供するか |
| 0:08〜0:35 | 一つの入力から結果までを示す |
| 0:35〜0:50 | 技術上の工夫または結果の証拠を一つ |
| 0:50〜1:00 | 実装できた範囲と中心の魅力で締める |

動画や画面一つで変化を理解できる場面を選ぶ。2024年の技育展参加者にも、1分版を動画と強みに絞った例がある。ただし、その年・段階の体験であり、現在の技育展の時間は[当該要項](https://geek.supporterz.jp/geekten/2026/information)を確認する。[参加記](https://kinkiknights.com/posts/273)

## 2分で短いデモと技術の説明を通す

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:15 | 利用場面と作品の一文説明 |
| 0:15〜1:10 | 入力、操作、結果のデモ |
| 1:10〜1:40 | 難所、自作部分、選んだ方法 |
| 1:40〜1:55 | 結果と、実装できた範囲 |
| 1:55〜2:00 | 最も覚えてほしいことを一文で締める |

MLHの巡回審査の配分例は、説明・デモ2分に質問・採点と移動を加える。ブースで何度も再開するデモなら、入力データと初期状態をすぐ戻せるようにする。[MLH](https://guide.mlh.io/general-information/judging-and-submissions/judging-plan)

## 3分で価値と技術を伝える

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:20 | 誰のどんな課題・体験を扱う作品か |
| 0:20〜1:35 | 代表的な一つのデモ |
| 1:35〜2:15 | 技術難所、判断、自作した部分 |
| 2:15〜2:40 | 検証・比較・完成度の証拠 |
| 2:40〜2:55 | 実装範囲、チームの貢献、次に直す点 |
| 2:55〜3:00 | 利用者が得る変化または作品の魅力 |

技育展2026とOpen Hack U 2025 TOKYOは、それぞれの要項で180秒を指定する。この配分はその指定から作成した提案で、運営の指定台本ではない。[技育展](https://geek.supporterz.jp/geekten/2026/information)、[Hack U](https://hacku.yahoo.co.jp/hacku2025_tokyo)

### 3分版の文の型

> ［作品名］は、［誰］が［どんなこと］をできる作品です。現在は［負担・制約・従来の操作］があります。ここで［入力］を使います。［操作］すると、［結果］になります。見ていただきたいのは［結果の箇所］です。難しかったのは［技術上の制約］で、［判断と方法］によって対応しました。［確認条件］では［事実］を確認しています。今回［実装した範囲］を作り、［残る点］は今後改善します。

架空の性能やユーザーの声で空欄を埋めず、確認できた情報を使う。楽しさが中心の作品では、無理に業務課題へ置き換えない。

## 5分で比較と達成度まで示す

| 時間 | 内容 |
| --- | --- |
| 0:00〜0:30 | 利用場面、目的、今回作ったもの |
| 0:30〜2:30 | 入力から結果までの実演 |
| 2:30〜3:35 | 技術難所、設計、代替方法との違い |
| 3:35〜4:15 | 検証結果、使い勝手、比較の条件 |
| 4:15〜4:40 | 目標に対する達成度、担当、残る点 |
| 4:40〜5:00 | 作品の価値・面白さと結び |

HP SCDSの2024案内は、最大5分の発表で、実用シナリオ、目標と達成度、長所・短所、技術、実演を含めるよう求める。一方、韓国の共同ハッカソン2023案内では5分は質疑込みである。後者なら、例えば3分説明・2分質疑に変更する。[HP SCDS](https://industriales.usal.es/2024/02/08/21348)、[韓国2023](https://meta.skku.edu/sw/notice.do?articleNo=155562&attachNo=120791&mode=download)

提出動画の指定が30秒などの場合は、2〜3分版をそのまま使わない。指定された長さと形式に合わせ、代表的な変化が分かる箇所を選ぶ。[Space Apps 2025の例](https://spaceapps-v2-staging.s3.amazonaws.com/media/documents/Final_Space_Apps_2025_Judging_Guidelines_for_web.pdf)

## エンジニア審査員への想定質問

| 質問 | 先に答えること | 示す補足 |
| --- | --- | --- |
| 本当に動いているのか | ライブ・録画・モック・事前計算の別 | 入力と結果、実行記録、動作条件 |
| 自分たちは何を作ったか | 自作と既存の境界 | 主要処理、ライブラリ、外部API、開発差分 |
| 何が難しかったか | 制約と選んだ方法 | 試した別案、失敗、変更と結果 |
| 何が新しいのか | 従来の体験や技術との違い | 同じ条件での比較、利用場面 |
| その技術を選んだ理由は | 目的に合う判断 | 速度・費用・精度・機器等の条件 |
| 誰に役立つか、何が面白いか | 対象者と価値 | 観察、試用、操作体験。未検証ならその旨 |
| 失敗する場合はあるか | 現在の限界 | 入力条件、例外、回避方法、次の検証 |
| その数字はどのように測ったか | 条件、対象数、基準 | 比較記録。推定値と実測値の区別 |
| 期間内にどこまで作ったか | 開発前後の差分 | 提出コミット、既存コード、追加機能 |
| 誰が何を担当したか | 実際の分担 | 連携した部分、担当者が答えられる詳細 |
| 次に何を直すか | 最も価値がある改善一つ | 現時点の制約と、確認する方法 |

回答は、結論と具体例から始める。詳しい実装は担当者へ引き継ぐが、短時間で何度も話者を交代しない。不明な数字をその場で作らない。

## 開発と発表の時間を分ける

Devpostの助言集には、台本や提出ページを早めに作り、終盤に録画・編集・アップロードの時間を確保する経験談がある。必要な時間は提出形式と環境で変わるため、全チームに同じ時間数を当てはめない。[Devpost](https://info.devpost.com/blog/6-tips-for-making-a-hackathon-demo-video)

1. 開発前半で、最後に見せたい一つの利用の流れを決める。
2. 初めて動いた時点で短い記録を残し、入力と再現方法を共有する。
3. 締切前に機能追加を止める時点を自分たちで決め、統合・実演・提出へ時間を使う。
4. 動作する版、資料、動画、提出ページの内容をそろえる。公式のコード凍結規則を守る。
5. 本番のPCと共有方法で通し、質問と障害時の切替も試す。
6. 初見の人に、何が動いたか、何が独自か、何が未実装かを言い直してもらい、誤解を直す。

## 発表設計シート

| 項目 | 記入欄 |
| --- | --- |
| 大会・年度・段階・狙う賞 | ［公式要項のURLと確認日］ |
| 発表と質問の時間 | ［別枠か合計か、接続時間を含むか］ |
| 評価項目と示す場面 | ［採点項目→操作・結果・説明］ |
| 一文の作品説明 | ［対象者と体験］ |
| デモの入力と結果 | ［どの初期状態から何を確認するか］ |
| 技術難所と自作部分 | ［制約→判断→実装→証拠］ |
| なぜこのチームか | ［経験や知識が変えた設計］ |
| 実装・録画・モックの範囲 | ［実際に示す版と条件］ |
| 失敗時の代替 | ［切替の条件、手元のファイル］ |
| 提出と再生確認 | ［締切、公開範囲、確認担当］ |
