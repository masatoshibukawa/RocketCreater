# 専門知識とClaudeの価値を示す3分デモ

確認日: 2026-11-07。今回の日本大会の提供資料と、[大会比較](02-events-and-domain-expertise.md)・[作品比較](03-winners-and-counterexamples.md)から導いた制作案である。公式指定の秒単位構成ではない。未実装の機能や未測定の改善を、実演台本の事実として埋めない。

## 中心となる一文

> 私たちは［具体的な現場・経験］から［見落とされやすい問題］を知っています。その知識を［制約・データ・評価］にし、Claudeと［検証・実行する仕組み］をつないで、［具体的な利用者］が［成果］を得られるようにしました。

角括弧は実際の経験と実装で埋める。経歴だけの自己紹介では、体験とのつながりが見えにくい。利用者、経験、判断基準、実装、結果が一続きになるようにする。

「世界初」「自分たち以外には不可能」とする主張には広い先行調査が必要になる。短い発表では、チーム固有の経験がどう判断に効いたかを示す方が確かめやすい。

## 「なぜ自分たちか」を証拠へ変えるワークシート

| 埋める問い | 探す素材 | 製品の中で対応する証拠 |
| --- | --- | --- |
| 実際に誰がどこで困ったか | 自分の制作・研究・現場記録、許可を得た利用者への聞き取り | 利用者と場面が分かる入力例 |
| 初心者や汎用AIが見落とす点は何か | 失敗例、例外、資料の読み違い、判断の分岐 | その条件を検出する処理 |
| なぜその出力が良いと分かるか | 専門家の判定、参照値、再現できる計算、比較基準 | 元資料と判定を辿れる結果 |
| なぜ既存手順では届かないか | 作業の分断、必要な熟練、入力の負担 | 専用の操作と、一貫した状態・成果物 |
| 自分たちの知識を外すと何が悪化するか | 同条件での比較、知識を入れる前の出力 | 具体的な一件の違い |

利用者と専門家の協力を、本人が製品を推薦したかのように表現しない。評価した事例数、評価者の役割、利用許可の範囲を記録する。

## Claudeを使った価値を3つの場所で示す

| 場所 | 説明すること | 用意する裏付け |
| --- | --- | --- |
| 開発時 | 仕様、調査、実装、デバッグ、検証で何が進んだか | 課題・変更・確認結果が対応した開発記録 |
| 利用時 | モデルが何を読み、どの道具を選び、どの結果で再判断したか | 実際の入力、外部に説明できる判断理由、ツール結果、出力 |
| 専門知識との接続 | 人が与えた制約と、モデルの判断がどう結び付くか | 出典、検査、専門家による訂正、条件変更の例 |

APIを内部で使うなら、その必然性を利用者の作業から説明する。例えば、資料を読み、状態を保存し、検証ツールを呼び、返った値で候補を更新する一連の処理が成立することを見せる。モデル名や呼び出し回数だけでは、この価値を確認できない。

開発時にだけ使う構成なら、実行時も使っているように見せず、開発のどの難所を越えたかを示す。その構成が参加・受賞条件に合うかは、当該回の要項で別に確かめる。

## 説得力を確かめる比較の作り方

以下は今後の評価案で、今回実験して得られた結果ではない。

| 比較相手 | 確かめたいこと | 条件を揃えるポイント |
| --- | --- | --- |
| 従来の人手の手順 | 作業のどこが減り、何を得られるか | 同じ資料・目標・完了基準。準備・確認時間も記録 |
| 普通のチャットと手動の転記 | 専用アプリの状態管理・操作・成果物の価値 | 同じモデル・提供資料・道具へのアクセスと試行予算 |
| ドメイン固有の知識を入れない構成 | 現場の知識が何を改善したか | 同じ入力・モデル・出力形式、評価者と評価基準 |
| 固定ルールの処理 | LLMの入力理解や適応が必要な場所 | 定型例だけでなく、条件が変わる例と例外 |

少数のデモ用事例での成功を、一般的な精度や何万人分の効果へ拡張しない。件数と対象範囲を添える。開発に使った事例と、最後に確かめる事例を分けると、調整した一例だけを見せる問題を見つけやすい。

最小限の評価記録には、入力、期待結果とその根拠、モデル・版、実行条件、得られた結果、成功・失敗、所要時間、担当者を残す。モデルの再実行で結果が変わる場合は、成功した1回だけを全体の性能としない。

## 180秒の構成案

単独スライドの説明動画にせず、実際の画面、入力資料、判定、成果物を中心に収録する。短いナレーションと字幕で、専門外の人も変化を追えるようにする。[今回の条件](01-japan-and-chat.md)

| 時間 | 秒数 | 画面と伝えること |
| --- | --- | --- |
| 0:00–0:15 | 15 | 利用場面を示す。誰が何をできずにいるかを一文で伝える |
| 0:15–0:35 | 20 | 自分たちが知る失敗条件を、実際の資料や入力で示す |
| 0:35–1:10 | 35 | 要求を入力し、Claudeが条件を整理して候補・処理を作る |
| 1:10–1:55 | 45 | 検査で問題を発見し、その結果を使って修正する核の動作 |
| 1:55–2:25 | 30 | 条件を一つ変え、判断・出力が適切に変わることを示す |
| 2:25–2:45 | 20 | 根拠を確認し、次の作業で使える成果物を受け取る |
| 2:45–3:00 | 15 | 確認した範囲、Claudeの役割、利用者に渡せた能力を一文で結ぶ |

合計180秒。タイトル、無音、フェード、エンドカードも上限に含めて確認し、実際の書き出しは少し余裕を持たせる。公式の4配点を、動画の秒数に比例配分したものではない。

## RocketCreaterに置き換えたナレーションの骨格

次は埋め込み用の文章で、チームの専門歴や製品の完成を断言する台本ではない。

1. 「［対象の利用者］は、［設計上の具体的な判断］で止まります。」
2. 「私たちは［実際の経験］から、［見落とし］が起きることを知り、この検査を入れました。」
3. 「要求を入力すると、Claudeが［実装済みの役割］を担当します。」
4. 「こちらは［実装済みの計算・検査］の結果です。この条件を満たしていないため、［根拠に沿う変更］へ進みます。」
5. 「要求をここだけ変えると、［確認できた判断・成果物の変化］が起きます。」
6. 「［根拠］を確認し、［実際に出力できる成果物］を受け取れます。」
7. 「確認したのは［シミュレーション・評価事例等の範囲］です。［利用者の能力の変化］を、ここまで実現しました。」

3D表示は、判定の対象を見つけたり根拠を辿ったりできると、利用体験の説明になる。回転するモデルだけを長く映すより、判断と操作を接続する。

## 収録時に証拠を保つ

- 同じ入力・実行・成果物がつながっていることを確認する。異なる試行の成功画面を一連の自動処理のようにつながない。
- 事前計算、模擬データ、倍速、待ち時間の省略は、その箇所に表示する。実時間の性能値は実測に基づける。
- 失敗条件を意図的に与える時は、その意図が分かる入力にする。検査が実際に失敗を止め、修正後に再確認した記録を残す。
- UI上で、入力、検査の根拠、変更箇所、最終出力が読める大きさにする。長いログを読む負担を審査員へ渡さない。
- 音声を明瞭に収録し、字幕で専門語を補う。BGMを使う場合は発話・操作音を聞き取れる音量にする。選曲より実動作の理解を優先する。
- 別アカウント等で動画と公開リポジトリを開き、提出後は提出内容を読み戻す。今回制作した機能・コードの範囲を説明できるようにする。

一般的な画面収録・音声・公開確認は[実演と動画のガイド](../hackathon-demos/03-live-video-and-reliability.md)も参照する。

## 最後に選ぶ、動画の核

候補を「派手さ」「現場らしさ」だけで比べず、次の4点で選ぶ。

1. 初見の人が、利用者の困りごとと結果の違いを理解できる。
2. 自分たちの専門知識が、具体的な判断・検査として見える。
3. Claudeが担う役割を、実際の挙動から確かめられる。
4. 今回の制作範囲で、再現して収録できる。

例として、要求から候補を作り、検査で問題を発見し、修正して根拠付き成果物を得る導線がある。現在の実装に照らして成立する一件を選ぶ。実装の監査、性能測定、動画完成、提出操作は、この調査資料の作成とは別の作業である。
