# スキルの検証記録

確認日: 2026-11-07。

## 実施した確認

- skill-creator付属のquick_validate.pyで全31スキルの形式を確認した。YAML解析に必要なPyYAMLは一時フォルダへ配置し、パッケージの実行依存には含めていない。
- [validate_library.py](scripts/validate_library.py)で、51文書の分類網羅性、カテゴリとサブスキルの一致、相対参照がパッケージ内に収まること、全モジュール・文書へ到達できること、UIメタデータを確認した。
- 研究発表の6つの時間表の合計と、専門大会の7区間180秒の連続性を実ファイルから確認した。
- 下記の想定入力に対して、モジュールを選び、判断と成果物の骨格を実際に組み立てて机上確認した。

別のエージェントによる独立評価、音声・動画の実視聴、実利用者による理解テスト、モデル選択精度の統計評価は行っていない。下の入力は検証用で、RocketCreaterの実績・測定値ではない。

## 想定入力と、組み立てた出力

| 想定入力 | 使用したサブスキル | 確認した判断・出力 |
| --- | --- | --- |
| 質疑3分込み15分の研究発表を作る | research-talks、duration | 本編は12分＝720秒。15分の本編案をそのまま使わず、下の12分案を作成 |
| 顧客面談30分、最後の10分は相談 | proposals、duration | 説明・実演は20分、対話10分。市場規模や調達計画を主役にしない |
| 日本大会向け3分動画をスライド中心にする | provider-domain、demo-video-audio | 記録された今回の案内に合わせ、実画面と入力・検査・成果物へ変更。最新版は要照合 |
| 3MTでデモ動画とBGMを使いたい | research-outreach | 保存したUQ規則では静止1枚、追加音声・動画不可。一般動画の演出案をそのまま提案しない |
| APIクレジットがあるなら内部APIは必須か | provider-domain、source-research | クレジット配布から義務は推定しない。開発利用と実行時利用、当該要項の明文を分けて説明 |
| Finalist表示と作者の「2位」報告がある作品 | source-research | 公式Finalistと本人の2位報告を別列に記録。公式順位・トラック確定へ書き換えない |
| 字幕だけからTEDの視線と声の強弱を評価 | ted-analysis、speaking | 字幕から構成・反復は分析し、視線・抑揚・沈黙の実測は未確認として残す |
| 独立実験3回、各回100細胞を図にする | scientific-figures | 実験ごとの群と細胞内の値を区別。入力が指定した独立実験単位を保ち、300独立実験と数えない |
| 日本語の100万円を英語の投資家資料へ訳す | multilingual、fundraising | JPY 1 millionとする。通貨未変換でUSDへ置換しない。計画値と売上実績も混同しない |
| なぜ自分たちしか作れないかを強調したい | argument-evidence、provider-domain | 「経験した失敗→追加した制約→検査で検出した例」という証拠の枠を作る。専門歴や世界初を創作しない |
| 研究費のピッチで、まだない成果を魅力的に見せたい | grant-pitches | 予備的根拠と、今後の検証・成功条件・代替策へ分けた構成を作成。未取得の結果を成果にしない |
| 110人のスライド実験から、主張見出しで受賞率が上がると言えるか | slides、source-research | 対象・設計変更・結果指標に限定し、受賞率や見出し単独の因果効果は支持しないと回答 |

表のサブスキル名はすべて `presentation-` を付けた名前に対応する。入口は [SKILL.md](SKILL.md)。これらは成果物の作り方を確認するケースで、実際に上記の競技へ応募した結果ではない。

## 品質の限界

形式と参照の検証は、発表が実際に伝わることや受賞を保証しない。スキルから作った台本・図・動画には、それぞれの依頼に合わせた計時、実ファイルの表示・再生、対象者の理解確認が別途必要になる。
