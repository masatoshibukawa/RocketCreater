# 日本語AIナレーションの制作

この手順は、製品デモ、技術紹介、SF映像に声を付けるときに使う。モデルの比較と出典は [2026年11月7日の調査](../../../../research/2026-11-07/ai-narration.ja.md) を必要な範囲で読む。導入や性能は公式仕様と実機確認を分ける。

原理に基づく選定、長尺・多言語への拡張、品質が悪いときの修正箇所は [原理と原因の切り分け](tts-principles-and-diagnostics.md) へ進む。

## 生成方式を選ぶ

- **既成話者のTTS**：原稿を安定した一人の声で読む。まず比較する方式。日本語編集のAivisSpeech／VOICEVOX／Style-Bert-VITS2、指示対応のQwen3-TTS等が候補。
- **声のデザイン**：文章で声質を設計する。Qwen3-TTS VoiceDesign等。文ごとに再設計すると声が変わり得るため、長編では声の固定方法も決める。
- **許諾済み録音による声の複製**：Qwen3-TTS Base等。参照音声と書き起こしを対応させる。写真が使えることは声の複製の許諾にはならない。
- **本人の録音を編集する**：話者の間や強調を残したい場合の比較対象。AIで声を変換するなら、元の録音、変換モデル、出力の条件を別に記録する。

費用ゼロが必要なら、継続した無料枠と無料体験を区別する。AivisSpeech本体が無料でも、選ぶ話者モデルの商用条件は別。VOICEVOXはクレジットと音声ライブラリの条件を確認する。CPUで動く編集型TTSを使えば、動画生成でGPUを使っている間も作業しやすい。

「透かしなし」は、画面上のロゴ、聞こえる宣伝音、不可聴の識別情報、クレジット義務を別項目にする。不可聴透かしを組み込むと公式に説明するChatterbox等を、無条件の候補へ混ぜない。情報が見つからないことは不存在の証明ではない。

## 比較用の短い原稿を作る

冒頭、専門用語と数字、締めの3種類を含む合計20〜30秒程度を目安にする。実際の作品に合わせ、同じ原稿と近い音量で2〜3候補を比較する。長編を一括生成する前に、読みと声質を決める。

表示用原稿と発音用原稿を分ける。字幕の英語表記を、発音修正のためのカタカナへ置き換えない。辞書機能がある場合は固有名詞を登録し、ない場合は発音用文字列を修正する。SSMLを扱えるかはエンジンとモデルごとに確認し、非対応のTTSへタグを直接渡さない。

例：

| 表示 | 発音用の候補 |
| --- | --- |
| RocketWright | ロケットライト |
| Claude Code / Claude API | クロードコード／クロードエーピーアイ |
| LLM | エルエルエム |
| 18.857 m | 約十八・九メートル（精密値は画面に残す） |
| 内田 大智／渋川 雅人 | ウチダ タイチ／シブカワ マサト |

丸めた数値を読むときは「約」を付け、単位・符号・未達の判定を失わない。名前の読みは本人が確認した表記を引き継ぐ。

声の指示は、役割、声質、話速、強調箇所を分ける。例：

> 落ち着いた日本語の技術ドキュメンタリー。少し低めの中音域。冒頭は期待を感じさせ、仕組みの説明は明瞭に。「予測」「未達」「予定」を聞き取れるようにする。

この例は制作上の案であり、特定モデルで有効な構文ではない。エンジンが対応する設定に変換する。AivisSpeechではVOICEVOXと同名でも意味の違うパラメータがあり、クエリをそのまま移植しない。Qwen3-TTSの演技指示対応もモデルサイズ・種類で確認する。

## 一文ずつ改善する

1. 意味のまとまりで区切り、文IDと使う場面を付ける。単語ごとの細切れは自然な抑揚を壊すため避ける。
2. 採用した声を固定し、素のWAVを残す。話者、モデルの版、辞書、演技、シード（対応時）、生成設定を音声と対応させる。
3. 比較結果を、発音、間、自然さ、声の一貫性、実尺、生成時間で記録する。ASRによる読み戻しは脱落・反復の補助検査に使い、アクセントや演技の合格判定にはしない。
4. 誤読なら辞書・発音用文字列、棒読みなら文の区切り・演技、尺超過なら原稿・間を変える。変更した文と接続部分を生成し直し、前後も試聴する。
5. 解決したら採用テイクを明記する。再生成しても再現しない不具合は、別の声や方式で比較する。

生成時間を比べるなら、初回モデル読込、合成、ファイル出力を分ける。RTFは「合成時間÷出力音声の長さ」で記録し、異なるPCや条件の広告値と混ぜない。

## 動画の尺と音を合わせる

- 音声を採用した後、文の開始・終了と余白を測り、字幕と場面転換を合わせる。映像の枠が固定されている場合は、まず原稿を短くする。
- 小さな速度変更は比較して使う。FFmpegの`atempo`で音の高さを保っても、急ぎすぎる話し方までは直らない。
- 元のWAVは合成時のサンプルレートで保存する。編集・納品時に必要なレートへ変換し、24 kHz等を48 kHzに変換しただけで音質が向上したとは扱わない。
- ナレーション単体を確認してからBGM・効果音を加える。強い残響や常時低音の追加は、明瞭さを聞き比べて決める。
- 最終ミックスでラウドネスとトゥルーピークを測る。必要なら2パスの`loudnorm`等を使い、納品先に合った目標を選ぶ。ピーク正規化だけをラウドネス検証と報告しない。
- 書き出したMP4を頭から末尾まで再生し、音切れ、字幕、動画との接続を確認する。デコード成功、数値検査、実際の試聴を分けて記録する。

## このプロジェクトでの引継ぎ

仮v1の [発音用文字列を含む編集データ](../../../../product-demo/preview-v1.json) と [既存の音声生成](../../../../product-demo/tools/preview_voice.ps1) はWindows音声Haruka用。AivisSpeechやQwen3-TTSを調査しただけで、この生成経路が置き換わったとは扱わない。新しいTTSを導入する場合は、ComfyUIやアプリの環境に依存関係を追加せず、専用環境または公式配布を使う。

素材は`output/media/product-demo/audio/`等のGit対象外領域へ、再利用する設定や原稿は制作側へ保存する。ナレーションの声を変更しても、解析が未達であることや、Claude APIが移行予定であることなど、デモが示す事実は維持する。
