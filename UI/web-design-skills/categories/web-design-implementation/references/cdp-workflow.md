# CDPを使う実装・確認

ブラウザ確認の待ちや取得に時間がかかる場合、またはサイトの性能を調べる場合だけ読む。通常の画面修正へ必ずCDPを追加する指示ではない。

## 目的と手段

- 自動化の時間を減らす: 起動・接続・待機・コマンド往復・取得量のどこが支配的か測る。検証用セッションの再利用、限定した読み取りの一括化、目的に合う撮影範囲を選ぶ。
- サイトを速くする: 遅い読み込みや操作を再現し、Networkや短いトレースで原因を絞る。コード・配信を修正して同じ条件で再測定する。
- 既存のブラウザツールや高水準APIで足りる操作はそれを使う。Chromium固有の観測だけCDPSessionを足せる。`connectOverCDP` は通常のPlaywright接続と同等の機能を保証する方式ではない。

CDPの利用は、利用可能なツール・権限の範囲で行う。日常利用のプロファイルへ勝手に接続しない。自分で起動を管理する場合は対象版のリモートデバッグ要件を確認して検証用プロファイルを使い、自分で作った資源を後始末する。

## 正しい確認を速くする

準備完了は必要なUI状態や対象応答で判断し、期限を設ける。固定sleepや `networkidle` を一律の完了条件にしない。`force` やDOMからの直接clickを通常の利用者操作の代わりにして速度を稼がない。

読み取りは件数と返す項目を限定し、同じタブの状態変更と並行実行しない。画像・フォント・CSSの遮断は画面を変えるため、通常の見た目確認や性能比較に混ぜない。寸法の取得だけでは重なりや読みやすさを証明しない。

`Performance.getMetrics` をWeb Vitals一式の測定とみなさない。詳細トレースは必要な期間・カテゴリに絞り、終了通知・データ欠損・ストリームの後始末を扱う。対象Chromeの版とexperimental/deprecated指定を原資料で再確認する。

## 結果の評価

変更前後で成果、データ、viewport/DPR、ブラウザ、通信・キャッシュ・Service Worker、計測負荷を揃える。自動化の所要時間とサイト性能を別に記録し、複数回の値・ばらつき・失敗率を残す。起動を除いた時間を作業全体の時間と呼ばない。ラボの一操作を全利用者のINPなどへ一般化しない。
