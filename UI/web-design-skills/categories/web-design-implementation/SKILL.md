# 設計を動く画面へ落とす

## 入力と実装

対象ファイル、既存の起動方法、画面の目的、実際の内容、API・データ・デザインシステムを確認する。新規制作でも、ユーザー指定の技術や公開先を尊重する。

- HTMLに意味と読み順を持たせる。移動はリンク、操作はボタン、入力には対応するラベルを使う。
- 大きな配置から実装し、内容に応じて列を増減させる。見た目の並べ替えが読み順・操作順を壊さないようにする。
- 空、入力不備、処理中、成功、結果なし、通信失敗のうち必要な状態を定義する。
- 画面文言は [コピーの基準](../web-design-copy/SKILL.md) を使い、実際の動作と合わせる。未接続のAPI、未実装の将来機能、未実施の試験を、ヒーローや特徴カードの文言へ自動で載せない。現在の操作に影響する条件は、その操作の近くに短く置く。
- 進捗を測れない処理へ架空の百分率を付けない。実際の完了・失敗と表示を対応させ、重複実行と再試行を扱う。
- CSSやSVGで十分な図へ、理由なく大量のJavaScriptや3D描画を追加しない。
- 実装依頼では実際に変更し、既存の手順で動作を確認する。設計助言だけの依頼へ実装や公開を追加しない。

キーボード、フォーカス、画面幅、文字拡大、読み込み、通信失敗を変更に応じて確認する。AAの操作対象サイズ原則24 CSS pxと、44〜48pxなどのタッチ操作の設計目安を区別する。

## 成果物と確認

開発者向けに変更した画面・ファイルと理由、実際に実行した確認、未確認の状態を示す。サイト利用者向けには、現在の用事と操作に必要な内容を表示する。画像、動画、フォントで配置が動く場合は寸法確保や読み込み戦略を見直す。ラボの一回の点数を実ユーザー体験全体の保証にしない。

適切な実行環境がない場合は独立した確認を進め、阻害要因を具体的に報告する。存在しないブラウザ・API・試験の結果を補わない。

## 作業用テンプレート

入力・通信・処理を伴う画面では、[状態と確認の表](references/state-and-verification.md) を必要な範囲で使う。

ブラウザ確認の高速化やサイト性能の診断には [CDPの使い分け](references/cdp-workflow.md) を読む。自動化の所要時間と、サイト自体の読み込み・操作性能を別に測る。

デプロイ・公開・無料ホストの選定には [公開の判断と確認](references/deployment-workflow.md) を読む。公開対象の動作と費用を見積もり、プレビューと本番の範囲を分ける。
