# 設計を動く画面へ落とす

## 入力と実装

対象ファイル、既存の起動方法、画面の目的、実際の内容、API・データ・デザインシステムを確認する。新規制作でも、ユーザー指定の技術や公開先を尊重する。

- HTMLに意味と読み順を持たせる。移動はリンク、操作はボタン、入力には対応するラベルを使う。
- 大きな配置から実装し、内容に応じて列を増減させる。見た目の並べ替えが読み順・操作順を壊さないようにする。
- 空、入力不備、処理中、成功、結果なし、通信失敗のうち必要な状態を定義する。
- 進捗を測れない処理へ架空の百分率を付けない。実際の完了・失敗と表示を対応させ、重複実行と再試行を扱う。
- CSSやSVGで十分な図へ、理由なく大量のJavaScriptや3D描画を追加しない。
- 実装依頼では実際に変更し、既存の手順で動作を確認する。設計助言だけの依頼へ実装や公開を追加しない。

キーボード、フォーカス、画面幅、文字拡大、読み込み、通信失敗を変更に応じて確認する。AAの操作対象サイズ原則24 CSS pxと、44〜48pxなどのタッチ操作の設計目安を区別する。

## 成果物と確認

変更した画面・ファイルと理由、実際に実行した確認、未確認の状態を示す。画像、動画、フォントで配置が動く場合は寸法確保や読み込み戦略を見直す。ラボの一回の点数を実ユーザー体験全体の保証にしない。

適切な実行環境がない場合は独立した確認を進め、阻害要因を具体的に報告する。存在しないブラウザ・API・試験の結果を補わない。
