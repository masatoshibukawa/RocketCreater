# Webバックエンドを設計する

まず利用者の主操作を一つ取り、ブラウザ、API、保存、外部処理のどこに変更が必要かを確認する。静的配信や既存サービスだけで目的を満たせる場合は、その構成を使う。調査依頼は資料と判断基準にまとめ、実装や外部サービスの作成は依頼範囲に従う。

- **既存の構成を起点にする。** CRUD中心ならBaaS、独自ロジックなら既存API、長時間処理なら状態を保存できるworkerを検討する。複数サービスに分ける理由を、処理時間・障害・保存・資源の違いで説明する。
- **所有者を操作ごとに確認する。** 認証情報を検証し、読み書き・ダウンロード・実行を対象ごとに認可する。ブラウザへ公開するキーとサーバーの特権キーを分け、BaaSのRLSやRulesを別利用者で確認する。
- **長い処理の状態を残す。** 受付と成功を分け、入力版、試行、期限、重複、再開、成果物を扱う。接続が切れても状態を照会できる設計にし、結果は対応する入力版で検証する。
- **無料枠は合算して判断する。** 実行、DB、認証メール/SMS、ファイル、転送、キュー、外部APIを分ける。継続無料・試用・課金契約内の無料量、集計単位、停止と課金を現行公式資料で確認する。
- **実際の動作に対応する証拠を残す。** 実装依頼では、利用者の操作からAPI・データ・結果を通す。公開後に必要な権限、切断、再起動、超過時の確認は対象に合わせて選ぶ。画面だけで保存や処理完了を確認したとは言わない。
