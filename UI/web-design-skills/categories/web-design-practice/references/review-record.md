# 練習・レビュー・利用確認の記録

依頼の種類に合う節だけを使う。チェック項目を埋めること自体を目的にしない。

## 学習課題

```text
今回練習する判断:
使う実際の内容:
制約（単色、一書体、動きなし等）と選んだ理由:
完成させる小さな成果物:
比べる条件:
振り返りの問い:
```

制約は練習用であり、以降の全制作の禁止規則にしない。

## レビューの一件

```text
対象の画面・状態:
観察できた事実:
影響する利用者の用事:
優先度と理由:
修正案:
確認方法と実際の結果:
未確認・依存する条件:
```

操作できない問題、誤読につながる問題、視覚的な改善提案を区別する。主張に必要な画面やデータを見ていない場合は、指摘を仮説として扱う。

文章では、強調のための括弧、対象や動作が分からない比喩、意味のない留保、サイトへ転記された開発メモを確認する。修正によって直接引用や重要な利用条件を壊していないかも点検する。

## 利用者に頼む課題の例

- このサイトでできることを説明する。
- 最初の操作を見つける。
- 二つの案の違いを読み取る。
- 結果の条件や根拠を探す。
- 入力不備や通信失敗からやり直す。

誘導する説明を足しすぎず、迷った場所、誤解した言葉、できなかった操作を記録する。少人数の観察を全利用者への統計的な証明としない。

## 確認の範囲を閉じる

重要な判断・修正に対応した確認ができたかを見直し、未確認を残した場合は理由を書く。自動検査の合格、色ペアの合格、目視確認を、全面的なアクセシビリティ監査と呼ばない。
