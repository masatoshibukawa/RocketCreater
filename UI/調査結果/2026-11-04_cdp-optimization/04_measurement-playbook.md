# 測定と比較の進め方

## 目的を一つ決める

最初に、何が終わるまでを速くしたいか決める。例えば次の二つは別の測定になる。

- 制作作業: PC幅・スマートフォン幅で主見出しと横はみ出しを調べ、必要な画面を保存するまで。
- サイト性能: 同じデータの結果画面を開き、指定した操作への表示更新が終わるまで。

どちらも、変更前後で得る成果と成功条件を同じにする。速くなっても画面を確認できなくなったケースは成功に数えない。

## 比較条件を残す

| 条件 | 記録する内容 |
| --- | --- |
| 実行環境 | OS、ブラウザとクライアントの版、headless/headed、実行機の負荷 |
| 接続 | ローカルか遠隔か、新規起動か再利用か、同時実行数 |
| ページ | 対象ビルド、URL、データ、ログイン状態、操作手順 |
| 表示 | viewport、DPR、言語、テーマ、動き軽減、フォント・画像の準備状態 |
| 通信 | 制限なし/制限値、HTTPキャッシュ、Service Worker、初回/再訪 |
| 記録 | 有効ドメイン、トレース設定、撮影範囲と形式、開始・終了条件 |

実ユーザーから集めるfieldデータと、環境を揃えるlabデータは目的が違う。ラボでは原因の再現と変更比較を行い、実際の利用状況の改善は適切なfieldデータでも確かめる。[labとfieldの違い](https://web.dev/articles/lab-and-field-data-differences) [D10]

## 実践用の比較手順

これは本資料の提案であり、固定の試行回数を要求する規格ではない。

1. 元の手順で、成功条件と所要時間の内訳を残す。起動・接続を含めるかを先に決める。
2. 変更はまず一つ選ぶ。例: 固定待機を結果表示待ちへ変える、情報取得を一括化する。
3. 初回の準備と繰り返しを分ける。初回性能が目的なら、初回の結果を捨てない。
4. A/Bを交互に実行するなど、時間経過やマシン負荷の偏りを減らす。繰り返し回数はばらつきと必要な判断精度に応じて増やす。
5. 各回の生値、中央値、範囲、成功・失敗数を残す。少数回からp95の安定性を主張しない。失敗と再試行を黙って除外しない。
6. 実際の画面・操作も同じ条件で確認し、測定値と品質が両立した変更を採用する。

単純な短縮率は `(変更前の代表時間 - 変更後の代表時間) / 変更前の代表時間 × 100`。代表値だけでなく試行数とばらつきを添える。差がノイズに埋もれる場合は、効果不明と記録する。

## 記録テンプレート

```text
目的・同じ成果とみなす条件:
対象ビルド・画面・データ:
ブラウザ/クライアント/接続方式:
viewport/DPR/フォント/画像/動きの条件:
通信/キャッシュ/Service Worker:
起動を含めるか・並行負荷・計測設定:
変更点:
各試行の開始・終了条件:
各回の時間・コマンド数・取得量・成功/失敗:
中央値とばらつき:
画面と実操作の確認:
採用する変更と理由:
```

サイト性能を調べる場合は、コマンド数の欄を埋めるより、対象のLCP・操作遅延・レイアウト変化や通信の内訳を残す。何を単位として集計した値かを明示する。

## このリポジトリで試す場合

既存の `web/` アプリの起動・ビルド手順に合わせる。性能値を比較するときは開発サーバと本番相当ビルドを混ぜず、同じ画面・データ・API条件にする。別のUIアプリを追加する必要はない。

最初の候補は、画面幅ごとの見出し・はみ出し取得の一括化、結果表示を条件にした待機、変更領域の撮影である。サイト自体を改善する場合は、遅い操作や読み込みを実際に記録してから対象を選ぶ。この調査ではアプリの起動・接続・速度測定を行っていないため、上記は実験候補である。
