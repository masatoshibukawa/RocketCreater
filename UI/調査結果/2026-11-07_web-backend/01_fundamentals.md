# バックエンドの基礎と構成

バックエンドは、ブラウザからの要求を受け、入力を検証し、権限と業務ルールに従ってデータや処理を扱う部分。表示を隠すだけでは実行権限を制限できないため、変更・取得する対象ごとにサーバー側の判断が必要になる。

## 役割を分けて考える

| 要素 | 受け持つ仕事 | 別に確認するもの |
| --- | --- | --- |
| API | 入力検証、認可、状態の変更、結果の返却 | 期限、サイズ、エラー、重複要求 |
| 認証 | 誰がアクセスしているかを確かめる | セッション期限、回復、メール・SMS |
| 認可 | その人がその対象へ何をできるかを決める | 所有者、所属、公開範囲、管理者操作 |
| データベース | 関係するデータと制約を永続化する | schema変更、接続数、検索、復旧 |
| オブジェクト保存 | 画像、PDF、ZIP、動画などを保存・配る | 閲覧権限、URL期限、容量、転送 |
| ジョブ・worker | 長い処理を受け付け、状態を保存して実行する | retry、重複、停止、並行数 |
| キャッシュ | 再利用できるデータを短時間保持する | 失効、正しい版、利用者間の分離 |
| 運用 | ログ、監視、secret、デプロイ、復旧 | 保存費用、通知、権限、手順 |

単純な構成では同じプロセスが複数の役割を担える。処理時間、障害、保存や資源の寿命が異なるときに分離を検討する。

## 主な構成

### BaaSを使う

SupabaseやFirebaseのSDK/API、認証、DB、保存を組み合わせる。CRUD中心なら自作APIを減らせる。ブラウザから直接アクセスする構成では、DBのRLS・grantsやFirebase Security Rulesが認可の中心になる。使うだけで他人のデータから自動的に分離されるわけではない。[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) [B15]、[Firebase Rules](https://firebase.google.com/docs/rules/basics) [B24]

### 一つのAPIを作る

Next.js等のサーバー機能、Node系API、PythonのFastAPI等で入力・業務ロジック・保存を扱う。既存の言語、ライブラリ、デプロイ先に合わせる。小さなAPIに、必要のない別言語や複雑なサービス分割を追加しない。

Pythonの数値計算や既存ツールを使うならFastAPIなどのPython APIは自然な候補。短い処理とCPUを長く使う処理を同じリクエスト内へ詰め込む前に、実行時間と資源を見積もる。

### APIとworkerを分ける

APIは受け付けと状態照会を行い、workerが長い処理を実行する。DBにジョブ状態、オブジェクト保存に成果物を置く案がある。FastAPIの `BackgroundTasks` は小さな後処理に使えるが、重い処理にはCelery等の別プロセス・別サーバーも公式資料で案内される。[Background Tasks](https://raw.githubusercontent.com/fastapi/fastapi/master/docs/en/docs/tutorial/background-tasks.md) [B01]

## APIを先に具体化する

画面の主操作について、入力、所有者、処理、保存、結果を一行にする。例えば、設計要求を登録する操作なら次を決める。

- 受け付ける値、型、単位、上限、必須項目。
- 誰がどの設計を読める・編集できるか。所有者は検証した認証情報から決める。
- 同じ要求を再送した場合に、同じジョブを返すか、新しい処理を作るか。
- すぐ返せる結果と、後から取得する結果。成功、入力不備、権限不足、資源不足、失敗の区別。
- どの版の入力・処理から生じた結果かと、結果の保存・削除期間。

IDがランダムでも、対象を読む権限の代わりにはならない。APIでクライアントから受け取ったIDを使うたびに、その人がその操作をできるかを確認する。[OWASP Object Level Authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/) [B31]
