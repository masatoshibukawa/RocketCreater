# 作り方・公開の確認・無料枠の見積り

## 小さな一連の操作から作る

1. **操作を一つ決める。** 例: ログインした利用者が設計要求を保存し、自分の一覧から開き直す。入力・出力・失敗・所有者を決める。
2. **既存構成へ接続する。** CRUD中心なら既存のBaaS、独自処理があれば既存APIを優先する。DBスキーマとマイグレーション、環境別の接続設定を用意する。
3. **認可と保存を通す。** 利用者A・Bで同じIDへアクセスし、許可と拒否を確かめる。再読込、API再起動、DB接続失敗時も必要な状態が分かるようにする。
4. **必要な処理だけ分離する。** 長時間ジョブ、ファイル配布、外部APIが必要なら、永続状態、制限、再試行、結果の版を足す。短いAPIへ最初から多数のサービスを追加しない。
5. **公開する環境で確認する。** APIの起動・`PORT`・health、DB接続、利用者権限、フロントからの通信、ログと復旧を確認する。手順の入口は [前回の公開例](../2026-11-07_web-deployment/04_deployment-playbooks.md)。

## 試算の例

値は例のために置いたもの。実測結果や請求額ではない。`GB` / `GiB`、要求 / 行、実行時間 / CPU時間を揃えて比較する。

| 場面 | 仮定と計算 | 判断 |
| --- | --- | --- |
| Firestoreで一覧表示 | 1,000人/日 × 30ドキュメント × 2回サーバーから取得 = 60,000読取/日 | Standardの50,000/日の例を超える。index読取やlistenerの再接続も別に確認 [B21][B34] |
| NeonのDBが常時activeの場合 | 0.25 CU × 24時間 × 30日 = 180 CU-hours | Freeの100 CU-hours/projectを超える仮定。実際にはscale-to-zero、負荷、同時接続で変わる [B20] |
| Cloudflare Queues | 小さな1メッセージをwrite/read/deleteの3操作と仮定。10,000 ÷ 3の整数部分 = 3,333メッセージ/日 | retry、分割、失敗等を含まない理想計算。APIやworker実行枠は別 [B27] |
| 解析処理 | 2 vCPUの割当で180秒 × 1,000回 = 360,000 vCPU秒 | 使う製品の課金方式、メモリ、試行、転送、GPU等を足す。request-basedの枠をJobsへそのまま適用しない [B04] |

根拠: [Firestore課金](https://firebase.google.com/docs/firestore/pricing)、[Neon料金](https://neon.com/pricing)、[Queues料金](https://developers.cloudflare.com/queues/platform/pricing/)、[Cloud Run料金](https://docs.cloud.google.com/run/pricing)。

## 支出を小さく始める

- **計算しないで済むものを分ける。** 公開見本は事前生成。再計算の要否は入力版と条件で判断し、古い結果を新しい結果として返さない。
- **一覧を小さくする。** 必要な項目、ページ、条件だけ読み、巨大な履歴・画像を一覧ごとに転送しない。D1では文数だけでなく読み取った行数、Firestoreではドキュメントや対象indexの読み取りを見る。[D1料金](https://developers.cloudflare.com/d1/platform/pricing/) [B25]、[Firestore課金](https://firebase.google.com/docs/firestore/pricing) [B34]
- **待機の費用を区別する。** 常時ポーリングでDBが休止できなくなる場合や、少数の常時接続がリソースを使う場合を測る。SSEやリアルタイムを採用しても、接続・送信・購読のコストは消えない。
- **長い処理を制限する。** 1人あたりの並行数、入力サイズ、試行数、期限を設定し、重複実行を避ける。動画・ZIPは必要になったときだけ取得する。ログは処理ID、時刻、時間、結果など目的に足る項目を選ぶ。
- **継続費用を足す。** DB、認証のメール/SMS、オブジェクト、キュー、API/LLM、build、ネットワーク、ログ、バックアップを別に確認する。通知設定だけで支出が止まると仮定しない。

## 公開前の動作確認

| 観測したい失敗 | 確認方法 |
| --- | --- |
| 起動できない・別のDBにつながる | 環境を分け、healthと一件の保存・読取を実URLで通す |
| 他人のデータが見える | 別利用者・未ログインで、APIと直接取得URLの両方を試す |
| 送信が二重になる | 同じ要求を繰り返し、受付・課金対象・成果物の件数を確認 |
| 再起動で結果が失われる | 検証環境で処理途中の中断、状態の再読込、再開・失敗を確認 |
| 容量・期限・料金が枠を超える | 代表データの大きさと時間を計測し、上限時の画面と復帰条件を確認 |
| 更新後に古いデータが読めない | バックアップを別環境へ戻し、旧schemaとの整合を確認 |

簡単な試作から始める場合も、利用者へ返す状態、アクセス権、料金上限に関わる項目は確認しておく。
