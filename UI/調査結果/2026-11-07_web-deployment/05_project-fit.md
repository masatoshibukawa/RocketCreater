# RocketWrightに当てはめる場合

この整理は `main` の `7f2183c` を基準にした配置案。公開済みの版や、この構成の動作確認を意味しない。

## 現行構成から分かること

- [Next.js設定](../../../web/next.config.ts) では `/backend/:path*` を `ROCKETWRIGHT_API_URL` へrewriteする。既定値は `http://127.0.0.1:8000`。[Webの起動説明](../../../web/README.md) ではこのURLをビルド時に設定するとしている。
- [FastAPI](../../../api/main.py) は設計の進行をSSEで配信する。クラウドへ配置するときはフロント→API→結果までが届くこと、途中イベントがバッファされず届くこと、切断と再試行を確認する。
- Next.jsの静的出力は現行rewriteを維持したまま置ける方式ではない。[Next.js 15 Static Exports](https://nextjs.org/docs/15/app/guides/static-exports) [H32]

| 見せたいもの | 配置の案 | 費用・確認 |
| --- | --- | --- |
| プロジェクト説明、動画への案内、結果例 | 承認済みの素材と保存済み結果で静的な紹介サイト | 提供URL・静的配信で開始しやすい。動画やZIPの転送は別に見積もる |
| 画面を触る公開デモ | 公開用データで範囲を限定したサンプル。実行内容が分かる文言にする | バックエンドを省ける操作は静的化。ライブ解析が必要な部分とは区別する |
| フル機能を外部から操作 | Next.jsのサーバーとFastAPIを、相互に届く環境へ配置 | SSE、時間上限、並行ジョブ、保存、認証、外部APIやGPU・ネイティブソルバーの費用を検証 |

**費用を抑えて紹介を公開するなら、静的な紹介・記録と、手元で動かす解析を分ける案が現実的。** 無料のフロントが表示されても、Pythonの計算やLLM、CAD・GPU処理を動かす基盤は別に必要になる。Renderの無料512 MBやWorkerのCPU枠が、このアプリ全体に十分とは評価していない。[Renderの枠](https://render.com/pricing) [H21]、[Workers制限](https://developers.cloudflare.com/workers/platform/limits/) [H07]

## 公開・最終提出の確認範囲

通常の作業プレビューと、最終提出で受け手に渡すものを分ける。最終提出を行う場合は、対象URL、アーカイブ、リポジトリで相手から見える範囲とcommitを確定し、実物を外部から開く。

- 公開ページと生成物のタイトル、ファイル名・パス、URLのホスト名、画像・動画のメタデータを確認する。
- リポジトリが提出物なら、相手が参照できるブランチ・タグ・コミット・PR等も対象に含める。不要な作業名は範囲内で直し、変更できない項目は提出方法を決める材料として報告する。
- 必須のAI利用申告、著作者、ライセンス、出典は保持する。公開物の取り違えを防ぐため、直したアーカイブは展開し、提出URLはログアウト状態で開き直す。

この調査での成果物は資料とskills。アプリのデプロイ、最終提出用アーカイブの生成、提出操作は行っていない。
