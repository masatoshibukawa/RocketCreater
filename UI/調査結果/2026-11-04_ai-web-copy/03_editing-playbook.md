# 03. 編集と配置の実践

以下の例は本調査で作成したものです。実在サイトから採取したコピーではありません。書き換え先で説明する機能が実際にある場合に使います。

## 1. 文章を先に具体化する

| 直す文 | 書き換え例 | 変更したこと |
| --- | --- | --- |
| あなたの「可能性」を「未来」へ | 設計案をシミュレーションで比較 | 強調括弧と抽象語を、対象と動作に変更 |
| 想いが軌道を描き、まだ見ぬ世界へ | 目標高度と積載物を入力して設計案を作成 | 比喩を、入力と得られるものに変更 |
| 新たな可能性を解き放つ | 解析を始める | 操作の直後に起きることへ変更 |
| 革新的でシームレスな次世代の体験 | 条件を変更して解析結果を比較 | 評価語の連続を具体的な作業へ変更 |
| 基本的には保存できる場合があります | 保存先を選択してください | 保存できる前提なら、必要な操作へ変更 |
| これは単なる解析ではなく、未来への第一歩です | 高度と速度の変化をグラフで確認 | 対比の決め台詞を具体化 |

短くするために機能や条件を作らないことが前提です。保存できるか未確認なら、まず仕様を確認します。

SGDSは、文に目的を持たせ、不要な修飾や説明を減らす方針を示しています。このような編集基準をAIへ渡す実務例として参考になります。[C20: Content](https://designsystem.tech.gov.sg/get-started/content)

## 2. 引用の意味を保つ

次の例は強調括弧とは用途が異なります。

- 実際の発言を正確に引用する。
- 本文で実際のボタン名やメニュー名を示す。
- 作品名、正確な入力文字列、引用内の引用を扱う。
- 表示見本で句読点や括弧そのものを確認する。

不要な強調を減らすために、これらの表記やコード中の文字列を一括削除しません。UI要素の表示自体をデザインで区別できる場合は、本文の表記は既存のルールへ合わせます。

## 3. 未完成事項を振り分ける

| 状況 | サイトに載せる内容 | 開発者向けに記録する内容 |
| --- | --- | --- |
| 使える解析に、未実装の将来機能がある | 現在使える解析の説明 | 将来機能の実装状況 |
| 予約画面のプレビュー | プレビューと分かる名前と操作。入力や送信の判断に必要な条件を、その近くに表示 | 予約APIや保存処理の接続状況 |
| 図がサンプルデータ | 図の近くのサンプル表示 | 実データとの連携状況 |
| 操作に料金・権限・保存範囲の条件がある | 利用者が判断する前に、具体的な条件を表示 | 内部の設計・処理方法 |
| 全端末の確認が完了していない | 理由なくヒーローや機能説明へ追加しない | 実施した確認と、未確認の範囲 |
| 実際にサービス障害が起きた | できること、次に行うこと、必要なら復旧状況 | 障害の技術的な調査情報 |

単に注意文を小さくするのではなく、現在の機能に合う画面・操作名・状態へ直します。GOV.UKのエラーメッセージは、問題と修正方法を示す文脈の資料です。将来機能の不足を説明する宣伝コピーとは分けます。[C10: Error message](https://design-system.service.gov.uk/components/error-message/)

## 4. 多言語の具体化の例

以下は、シミュレーション済みの設計案を比較できるサービスを想定した独自の例です。翻訳の正解や、各言語で確認された発生頻度を示すものではありません。

| 言語 | 抽象的な例 | 動作を示す例 |
| --- | --- | --- |
| 日本語 | 可能性を、次の未来へ | 解析済みの設計案を比較 |
| English | Unlock tomorrow’s potential | Compare simulated rocket designs |
| Français | Donnez des ailes à vos idées | Comparez les modèles simulés |
| Deutsch | Ideen für die Zukunft entfalten | Simulierte Entwürfe vergleichen |
| Español | Lleva tus ideas al futuro | Compara diseños simulados |
| 中文 | 让梦想照亮未来 | 比较仿真设计方案 |
| 한국어 | 가능성을 미래로 연결하세요 | 시뮬레이션 설계안 비교하기 |
| Português | Dê asas às suas ideias | Compare projetos simulados |

詩的な表現が依頼された広告や作品では、別の判断ができます。今回の既定では、通常のWeb機能紹介や操作文を具体的にします。

## 5. AIへ渡す編集条件

```text
対象の画面と読者:
現在できること:
読者が次にすること:
実際に必要な利用条件:
文章の用途（サイト本文 / 開発者向け報告）:

通常の文で対象・動作・結果を伝える。
強調用のかぎ括弧、求められていない比喩、
利用者に関係しない未完成事項の強調を追加しない。
直接引用や実際のUI名など、意味のある表記は保つ。
操作に必要な条件は、関連する操作の近くに短く置く。
機能・数値・実績について新しい事実を作らない。
```

## 6. 確認の観点

文の数や括弧の数だけで合否を判定せず、読者が何を理解し、何をするかで確認します。

- 見出しと説明だけでサービスの用途が分かる。
- ボタンと実際の次の画面・操作が一致する。
- 書き換え前後で機能・条件・引用の意味を保っている。
- 開発事情が、利用者の主情報として表示されていない。
- 利用者の判断に必要な条件は、見つけられる位置にある。
