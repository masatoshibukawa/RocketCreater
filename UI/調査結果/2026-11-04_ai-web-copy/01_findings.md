# 01. 現象を分けて考える

## 1. 今回の問題

対象は、Webサイトに表示する見出し、説明、ボタン、空・処理中・エラーなどの文言です。

| 現象 | 読み手に起きる問題 | 編集で確認すること |
| --- | --- | --- |
| 強調のためのかぎ括弧・引用符 | どの語も特別扱いになり、読みが途切れる | 引用の意味があるか。普通の文へ戻せるか |
| 詩的・抽象的なコピー | 何のサービスか、何ができるか分からない | 対象、動作、結果を説明できるか |
| 留保や前置きの連続 | 結論や次の操作が見つからない | 条件は実在するか。判断に必要な場所にあるか |
| 未完成事項の過剰表示 | 利用者が知る必要のない制作状況が主役になる | 利用者の行動と、開発者の進捗報告を分けたか |

この分類は本調査の作業上の整理です。外観や特定の語句からAI制作を判定する分類器ではありません。

## 2. 文章の偏りについての実証研究

Reinhartらは、同じ手がかりから人間と複数のLLMが書いた英語文章を比較し、語彙・文法・修辞の体系的な差を報告しています。モデルや調整方法で違いがあり、ジャンルに合う文体の変化にも課題があるという研究です。Webコピーや日本語のかぎ括弧だけを測ったものではありません。[C01: 研究本文](https://arxiv.org/html/2410.16107v2)

Kobakらは、生物医学論文の抄録で、LLMの普及後に特定のスタイル語が増えたことを分析しています。集団・時系列の語彙変化を扱う知見で、個々のWebコピーの制作手段や質を語句だけで断定する方法ではありません。[C02: 研究概要](https://arxiv.org/abs/2406.07016)

この二件から、生成された文章を常に無色の文体だと考えず、目的のジャンルに合わせて編集する必要性を検討できます。特定の単語を全面禁止すればよい、という結論にはしていません。

## 3. 留保を全削除する方法は採らない

Rathiらは、確信や不確実性を示す表現と、それを受け取る利用者の反応が言語間で異なることを調べています。日本語における不確実性の表現が、英語と同じように解釈されるとは限らない点も扱います。[C03: 多言語の研究](https://arxiv.org/html/2507.06306v2)

また、不確実性を言葉で適切に示せるかを評価する研究もあり、留保の過不足はそれぞれ別の問題です。[C04: EMNLP 2024](https://aclanthology.org/2024.emnlp-main.443/)

ここから今回採る方針は、曖昧な前置きを増やす代わりに、分かっている範囲と必要な条件を具体的に書くことです。Webサイトの未実装表示がどの程度発生するかを、この研究から推定しません。

## 4. 引用符・括弧の多用

日本語の実務記事には、語を括弧や記号で繰り返し強調することや、同じ型の文が続くことへの指摘がありました。個人の観察であり、統制した実験ではありません。[C18: Zennの実務観察](https://zenn.dev/fibujrsl/articles/4958a844214709)

SmartHRは括弧による補足の多用、冗長な表現、主観的で不要な否定的表現などを扱っています。かぎ括弧の全廃を指示しているわけではなく、UI名などの表記には独自の規則もあります。[C05: 記号の表記](https://smarthr.design/products/contents/idiomatic-usage/symbol/)、[C06: 書き方の基本](https://smarthr.design/products/contents/writing-style/)、[C07: ヘルプの書き方](https://smarthr.design/products/contents/help-center/basic-rule/)

Googleの技術文書ガイドも、引用符を使う場面を用途別に整理しています。英語の技術文書に対する同社の慣行なので、日本語の句読法へ機械的に移植しません。[C08: Quotation marks](https://developers.google.com/style/quotation-marks)

今回の判断は、意味のない強調をやめ、引用として意味を持つ表記を残すことです。記号だけを一括削除すると、発言者、画面名、正確な入力文字列が分からなくなる場合があります。

## 5. 詩的・抽象的なコピー

フランス政府の執筆ガイドは、具体的な語、能動態、比喩や迂言を減らす方針を示しています。Ant Designの中国語ガイドも、利用者になじむ直接的な言葉を選び、曖昧・過度に文雅な表現を避けると説明しています。[C15: フランス政府](https://www.info.gouv.fr/marque-de-letat/comment-s-adresser-aux-citoyens)、[C12: Ant Design](https://ant.design/docs/spec/copywriting-cn/)

Microsoftのフランス語の実務記事では、AI文章の冗長な語、曖昧な言葉、似た文の構造を編集する提案が見られました。販促も含むガイドであり、記事内の検出ツールに関する主張をAI判定の根拠として採用してはいません。[C19: Microsoftの解説](https://www.microsoft.com/fr-fr/copilot/ai-knowledge/humanize-ai-text)

今回の対象では、比喩を別の比喩へ置き換えるより、何を使い、何をして、何が得られるかを書きます。広告や作品の演出として詩的表現を明示的に求められた場合は、その依頼に合わせます。

## 6. 正しさと、全てを説明することを分ける

Tossの韓国語のライティング原則は、書き手が製品の背景を知っているために、今は不要な情報まで説明したくなる問題を扱っています。意味のない語・文・重複を取り除き、ボタンの次に起きることを伝える方針です。[C13: Tossの原則](https://toss.tech/article/21022)

GOV.UKは、説明を増やす前にUIを見直すことや、短く直接的な文にすることを勧めています。強い警告は、重要な結果を知らせる場面で使う部品として位置づけています。[C09: UIの書き方](https://www.gov.uk/service-manual/design/writing-for-user-interfaces)、[C11: Warning text](https://design-system.service.gov.uk/components/warning-text/)

これを踏まえた今回の設計方針は次の通りです。

- サイトの入口では、現在使える価値や次の操作を伝える。
- 将来機能や開発の不足一覧は、利用者向けの主見出しや特徴カードへ自動で加えない。
- 現在の操作へ影響する条件は、関連する操作の近くへ置く。
- 実際にできない操作を、できるように見せるコピーには変えない。
- 実装状況、テスト結果、未確認事項は、開発者向けの報告で扱う。

注意文を小さくすることだけで解決せず、機能の見せ方、操作の状態、文章の置き場所まで一緒に考えます。

## 7. 研究で言えたことと、今回決めたこと

| 内容 | 扱い |
| --- | --- |
| 一部LLMの語彙・文法・修辞に偏りがある | 対象モデル・コーパスに条件を持つ実証結果 |
| 留保の使われ方・受け取り方に言語差がある | 対象の課題・言語に条件を持つ実証結果 |
| 簡潔・具体的な文、不要な説明の削減 | 複数の実務ガイドに見られる設計方針 |
| 強調用かぎ括弧を既定で使わない | ユーザー指定に基づくスキルの方針 |
| 求められていない詩的コピーを使わない | ユーザー指定に基づくスキルの方針 |
| 未完成項目をサイトの主役にしない | ユーザー指定と実務ガイドを踏まえた設計方針 |

日本語のかぎ括弧の発生率や、各言語のWebサイトで未完成事項が強調される頻度は、この調査では測っていません。モデルの学習方法が三現象を直接引き起こすという因果関係も断定しません。
