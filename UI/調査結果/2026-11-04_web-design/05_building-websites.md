# 05. Webサイトを作る手順と実装の基礎

## 1. HTML・CSS・JavaScriptの役割

| 技術 | 主な役割 | 例 |
| --- | --- | --- |
| HTML | 内容と意味を構造にする | 見出し、段落、リンク、フォーム、表 |
| CSS | 配置と見た目を決める | 幅、余白、色、文字、レイアウト |
| JavaScript | 状態と振る舞いを扱う | 入力検証、通信、選択、結果の更新 |
| サーバー / API | 保存や処理を担う | 解析実行、ユーザー管理、データ取得 |
| ホスティング | 公開して配信する | HTTPS、ドメイン、デプロイ |

CSSは内容の意味を置き換えません。クリック可能な見た目を作るだけでなく、移動はリンク、操作はボタンとして実装します。学習の入口は [MDNのCSS基礎・スペイン語版](https://developer.mozilla.org/es/docs/Learn_web_development/Core/Styling_basics)（S11）です。

## 2. 目的に応じて制作手段を選ぶ

次は技術選択のための本資料の整理です。特定サービスの料金・現在の機能比較ではありません。

| 作りたいもの | 選択肢 | 最初に確かめること |
| --- | --- | --- |
| 小さな案内・作品集 | HTML/CSS、静的サイト、ビジュアル制作ツール | 更新する人、素材、独自ドメイン |
| 記事を継続更新するサイト | CMSや静的生成とコンテンツ管理 | 執筆・レビュー・公開の流れ |
| 対話や解析を伴うアプリ | 状態管理できるフロントエンドとAPI | 状態遷移、通信失敗、保存 |
| 大きなEC | 既存の商取引基盤 | 商品・決済・在庫・配送・運用 |
| 表現中心の体験 | HTML/CSS/SVGに必要な描画技術を追加 | 操作性、負荷、代替表示 |

学習初期はHTML/CSSで一画面を作り、必要な振る舞いだけ追加すると、どの層で問題が起きたか理解しやすくなります。既存プロジェクトに参加する場合は、その構成を尊重します。

このリポジトリのフロントエンドは `web/` です。今回の `UI/調査結果/` は調査資料の置き場で、第二の本番アプリを作る提案ではありません。

## 3. 制作を八つの成果物に分ける

1. **短いブリーフ:** 対象、目的、主操作、表現の方向。
2. **内容一覧:** 実際の文章、画像、図、データと出典。
3. **情報の順序:** 読者の疑問に答える順に並べる。
4. **ワイヤーフレーム:** 色を使わず、大きさと配置を確認。
5. **スタイルタイル:** 色・書体・線・角丸・動きの小さな見本。
6. **代表画面:** 最も重要な一画面と、空・処理中・失敗の状態。
7. **実装:** 意味あるHTML、可変レイアウト、必要な通信。
8. **検証と運用:** 端末、入力、拡大、読み込み、更新方法。

これは本資料の提案する進め方です。各段階で小さく試し、実際の内容から離れたまま大量の画面を作らないようにします。

## 4. 最小のページから始める

以下は学習用の完全なHTML例です。別の作業用フォルダへ `index.html` として保存するとブラウザで開けます。保存や通信を行う機能はありません。

```html
<!doctype html>
<html lang="ja">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>解析結果を根拠から読む | デザイン練習</title>
  <style>
    * { box-sizing: border-box; }
    body {
      margin: 0;
      background: #f7fafc;
      color: #102a43;
      font: 1rem/1.8 system-ui, sans-serif;
    }
    .wrap {
      width: min(70rem, calc(100% - 2rem));
      margin-inline: auto;
    }
    header { padding-block: 1rem; border-bottom: 1px solid #72869a; }
    main { padding-block: clamp(2rem, 6vw, 5rem); }
    h1 {
      max-width: 18em;
      font-size: clamp(2rem, 1rem + 3vw, 3.5rem);
      line-height: 1.3;
    }
    .grid { display: grid; gap: 2rem; }
    .grid > * { min-width: 0; }
    .summary { background: #fff; padding: 1.5rem; }
    a { color: #005ea8; text-underline-offset: 0.2em; }
    a:focus-visible { outline: 3px solid #7b3fe4; outline-offset: 3px; }
    @media (min-width: 52rem) {
      .grid { grid-template-columns: minmax(0, 2fr) minmax(0, 1fr); }
    }
  </style>
</head>
<body>
  <header class="wrap"><a href="#main">本文へ</a></header>
  <main id="main" class="wrap">
    <p>DESIGN STUDY / 学習用の見本</p>
    <h1>解析結果を、根拠から読む。</h1>
    <div class="grid">
      <section aria-labelledby="purpose">
        <h2 id="purpose">何を確かめる画面か</h2>
        <p>要求と結果を比較し、条件と根拠を確認する画面を考えます。</p>
        <a href="#check">確認項目へ進む</a>
      </section>
      <aside id="check" class="summary" aria-labelledby="check-title">
        <h2 id="check-title">確認項目</h2>
        <ul>
          <li>結果と条件を区別する</li>
          <li>失敗した理由を読む</li>
          <li>次の操作を見つける</li>
        </ul>
      </aside>
    </div>
  </main>
</body>
</html>
```

まず文章を自分の内容へ変え、次に列の比率と余白を変えます。一度に全てを変更せず、何が印象を変えたか観察してください。この例は完成品のアクセシビリティや全ブラウザ互換性を認定するものではありません。

## 5. レスポンシブを「縮小」から考えない

狭い画面では、列を減らすだけでなく情報の順序を考え直します。主操作、主結果、説明、詳細という意味のある順序をHTML側に持たせます。

[MDNのレスポンシブ解説](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/CSS_layout/Responsive_Design)（S17）は、可変幅、メディアクエリ、広い画面への段階的な拡張を説明しています。

確認する点:

- 画面幅で折り返すか。固定幅の子要素がはみ出さないか。
- CSSで見た目だけ順番を変えて、読み順と操作順が離れていないか。
- 表や図が必要とする幅と、ページ全体の幅を分けて扱っているか。
- 固定ヘッダーや下部操作が本文・フォーカス位置を覆わないか。

[WCAGのReflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html)（S42）は、縦スクロールの内容を320 CSS px相当の幅でも、情報・機能の損失や二方向スクロールなしに提示する条件を説明しています。地図・図・表など、二次元配置が必要な部分には例外があります。ページ全体を例外扱いしないようにします。

## 6. 正常画面以外も設計する

| 状態 | 必要な表示 | 次の操作 |
| --- | --- | --- |
| 初回・空 | 何を入れるか、入力例 | 入力する、例を使う |
| 入力不備 | 問題のある項目と理由 | 修正する |
| 送信・処理中 | 何をしているか、重複実行防止 | 必要なら取消 |
| 結果なし | 条件と、見つからなかった理由 | 条件を変える |
| 成功 | 結果、条件、根拠 | 比較、保存、次の解析 |
| 通信失敗 | 何が完了していないか | 再試行 |
| 一部のみ完了 | 完了した範囲と不足 | 続行、再試行、確認 |

処理中のバーは、進捗を計測できる場合だけ百分率で表します。計測できない場合は段階名や経過状態を示します。装飾のための偽の進捗を実処理の結果として表示しません。

## 7. 操作性とアクセシビリティ

[ターゲットサイズの最低条件](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)（S05）は、AAでは原則24×24 CSS px以上、または定められた間隔などの例外です。44pxをAAの一律最低値として説明しないでください。本資料では、主要なタッチ操作を44〜48px程度の高さから試すことを**実装上の目安**にします。

さらに、ラベルと入力の関連付け、キーボード操作、見えるフォーカス、適切な見出し、画像の代替テキストを確認します。色や動きの条件は [配色](03_color.md) と [SFデザイン](06_scifi-interfaces.md) を参照してください。

## 8. 速度も見た目の品質に含める

[Web Vitals](https://web.dev/articles/vitals)（S20）の良好な目安は、LCP 2.5秒以内、INP 200ms以下、CLS 0.1以下です。実ユーザーの75パーセンタイルで、モバイルとデスクトップを分けて評価します。

画像の寸法を確保する、不要なJavaScriptを減らす、フォントや動画を選別する、大きな描画を常時動かさない、といった対策を内容に応じて選びます。Lighthouseの一回の点数を実ユーザー体験全体と同一視しません。

## 9. 公開までの確認

ページのタイトル、リンク、404、入力・通信失敗、画像・フォントの権利、HTTPS、必要な設定、プレビューと本番の違いを確認します。機密情報をフロントエンドへ埋め込まず、問い合わせや購入がある場合は実際の受付・処理まで確認します。

公開後も、内容の更新担当、壊れたリンク、読まれない箇所、利用者が迷う箇所を見直します。制作は、最初のスクリーンショットを完成させた時点では終わりません。
