# 08. 学習・制作の実践計画とRocketWrightへの応用

本章は調査を踏まえた**提案**です。既存アプリを変更した記録ではありません。制作時間や学習効果を保証する計画でもありません。

## 1. まず一つ完成させる順序

| 回 | 作業 | 残すもの | 自分で確かめること |
| --- | --- | --- | --- |
| 1 | サイトの目的と文章を決める | 短いブリーフと実際の見出し・本文 | 誰が何をするか説明できる |
| 2 | 参考を集めて分解する | 主参考3件程度と採用理由 | 色、文字、構造、動きを分けて説明できる |
| 3 | 白黒で組む | 広い画面と狭い画面のワイヤーフレーム | 主役と主操作が分かる |
| 4 | 文字と余白を整える | 文字階層・幅・間隔のルール | 日本語の最長ラベルも読める |
| 5 | 色と図を加える | 役割別パレットと主図 | 数字と凡例を理解できる |
| 6 | 状態と動きを作る | 空・処理中・成功・失敗 | 各状態で次の行動が分かる |
| 7 | 実装を検証して編集する | 動く小さなページと確認記録 | キーボード・拡大・小画面で使える |

初学者なら一回を一日以上かけても構いません。完成画面を増やすより、理由を説明できる一画面を作る方を優先します。

## 2. 個別に上達する練習

| 練習 | 制約 | 学べること |
| --- | --- | --- |
| 一色のページ | 色の強弱を使わない | 階層、文字、余白 |
| 一書体のページ | 大量のフォントを使わない | ウェイト、サイズ、行間 |
| 一内容三案 | 同じ文章を三つの構図にする | 情報の優先順位 |
| カードなしのページ | 枠の反復に頼らない | 線、余白、編集構造 |
| 動きなしのSF画面 | ネオンと点滅を使わない | 図、数値、計器の意味 |
| 日本語の長文へ差し替え | 英語の短文でごまかさない | 改行、行高、可変幅 |
| 一つの状態を追加 | 通信失敗や結果なしを作る | 操作と説明の設計 |
| 参考の原理だけ採用 | ロゴ、画像、文言は流用しない | 観察から独自の設計へ変換 |

練習用の模写と公開作品を区別し、素材・文言・ブランドを無断で自分の作品として公開しないようにします。

## 3. RocketWrightなら何を主役にするか

リポジトリの仕様では、自然文の要求、設計探索、シミュレーション、比較、図面、出典が中心です。派手な宇宙背景より、**設計が検証される過程**そのものを見せ場にできます。

以下の三方向を比較する提案です。

| 方向 | 主役 | 表現 | 合いそうな場面 |
| --- | --- | --- | --- |
| 静かな研究端末 | 機体図と要求の達成状況 | Mission control、抑えた線と色 | デモ、設計比較 |
| 明るい解析ノート | 条件、説明、比較表 | Light lab、白い面と明確な文字 | 初心者、長い説明 |
| 編集的な科学展示 | 仕組みとストーリー | Editorial、大きな図と本文 | サービス紹介、学習 |

どれも採用は未決定です。まず同じ内容で試作し、見た目の好みと目的の達成を分けて評価します。

## 4. 画面の骨組み

下図は領域と読み順を考えるためのワイヤーフレームです。寸法や最終配色を決めた図ではありません。

```text
広い画面
┌─────────────────────────────────────────────┐
│ 名前 / セッション名 / シミュレーションの説明     │
├──────────────┬──────────────────────────────┤
│ 要求・入力     │ 主結果 / 条件 / 機体側面図       │
│              │                              │
│ 質問と回答     ├──────────────────────────────┤
│              │ 設計案の比較 / 主要な指標        │
│ 主操作         ├──────────────────────────────┤
│              │ 解析の進行 / 試行履歴           │
├──────────────┴──────────────────────────────┤
│ 詳細条件 / 解析モデル / 限界 / 数値の出典         │
└─────────────────────────────────────────────┘

狭い画面の基本順
要求 → 主操作 → 進行 → 主結果 → 比較 → 詳細と出典
```

解析中は進行を主役に、完了後は結果と比較を主役に切り替えると考えます。入力の編集途中に表示が勝手に移動しないようにし、更新でキーボードの焦点を奪わない設計を検討します。

## 5. 状態ごとの文章を用意する

| 状態 | 文言案 | 設計上の役割 |
| --- | --- | --- |
| 初回 | どこまで飛ばすか、何を載せるかを教えてください | 入力内容を具体化 |
| 質問 | 回収は必要ですか | 不足情報だけ尋ねる |
| 解析中 | 候補をシミュレーションしています | 実際の処理を説明 |
| 条件未達 | この条件を満たす候補は見つかりませんでした | 失敗と制約を区別 |
| 完了 | 条件を満たした案を比較できます | 次の行動を示す |
| 通信失敗 | 結果を取得できませんでした | 処理状況を誤認させない |

文言は実装時の状態に合わせて見直します。処理が完了していないのに「完了」と見せたり、再試行で二重処理を起こしたりしないようにします。

## 6. 数値とグラフの設計

- 値と単位を近くに置く。
- 目標と結果を同じ単位で比較する。
- 平均、公称、分位点、成功率を混同しないラベルにする。
- 合否の条件を開けるようにする。
- 出典ツール呼び出しID、モデル、環境条件へ進めるようにする。
- 図の拡大や詳細を、主要な操作の邪魔にならない場所に置く。
- 実データが未提供の試作は、架空の表示例であると分かるようにする。

ここでは新しい解析値を提案していません。実装ではリポジトリの方針に従い、数値はツールの戻り値から取得します。実在の測定装置と誤認させるラベルも避けます。

## 7. 制作前のチェック

- [ ] 対象と主操作を一文で説明できる。
- [ ] 実際の文章と素材がある。
- [ ] 参考のURL・制作者・採用理由を記録した。
- [ ] 主図と主操作を選んだ。
- [ ] 空・処理中・成功・失敗の状態を列挙した。
- [ ] 採用しない表現にも理由がある。

## 8. 画面のチェック

- [ ] 見出しだけでも内容の順序が分かる。
- [ ] 本文と補足を読める。
- [ ] 文字サイズ、太さ、余白の役割が一貫している。
- [ ] 色だけに意味を任せていない。
- [ ] パレットの実際の組み合わせを検査した。
- [ ] グラフに軸・単位・凡例・条件がある。
- [ ] 数字の桁や単位を比較できる。
- [ ] 装飾を外しても画面の目的が分かる。
- [ ] 意味のない枠やアイコンを整理した。
- [ ] 写真・図・フォントの権利と出典を確認した。

## 9. 操作と実装のチェック

- [ ] キーボードで主要な操作ができる。
- [ ] フォーカス位置が見え、固定領域に隠れない。
- [ ] 入力のラベルとエラーが対応している。
- [ ] 狭い画面でも主操作が見つかる。
- [ ] 拡大や文字間隔の変更で情報が失われない。
- [ ] 本文の読み順と見た目の順序が合っている。
- [ ] 動きを軽減した状態でも内容が分かる。
- [ ] 長く動く表示や更新に、必要な停止・制御がある。
- [ ] 通信失敗から回復できる。
- [ ] 処理の状態と表示文言が一致する。
- [ ] 画像やフォントの読み込み時に配置が過度に動かない。
- [ ] 実ユーザーの速度と応答を測る方法がある。

これはレビューの補助であり、全てのWCAG達成基準を網羅する監査表ではありません。数値要件と適用条件は各章の原資料を参照してください。

## 10. 評価を好みだけで終わらせない

試作を見せるときは、「かっこいいですか」だけでなく、次の行動を頼みます。

1. 何をするサイトか説明してもらう。
2. 最初の操作を見つけてもらう。
3. 二つの案の違いを読み取ってもらう。
4. 結果の根拠を探してもらう。
5. 失敗後のやり直し方を示してもらう。

見つけられなかった場所、迷った言葉、誤って理解した情報を記録します。その後、見た目の印象も聞きます。少人数の試作確認を統計的な証明とは扱わず、次の修正の材料にします。
