# RocketCreater：残る15項目を順に完了させる計画

作成日：2026-11-06。根拠は[全チャット・全ブランチ監査](completeness-audit-2026-11-06.md)。
計画作成時のmainは `26e86cc`、実装済みの制作経路は [PR #48](https://github.com/masatoshibukawa/RocketCreater/pull/48) / `38eb9a5`。
この文書の追加は計画の記録であり、下記の修正・実機試験を実施した記録ではない。

## 到達点

一般の利用者が日本語で依頼し、既存のローカルGemmaで要求と候補を整理できる。
計算結果と理由を見て条件を変え、同じ版の寸法・材料・取付・質量・機材から解析、CAD、印刷データ、組立手順、映像、ZIPを作れる。
実物の測定結果を設計へ戻し、再起動や別環境でも作業を再開・再生成できる。
最後に公開版・説明・提出物を揃える。課金APIの接続試験は、その後の最後の機能確認とする。

「画面が動く」「計算処理が終わる」「数値精度を満たす」「実物で確認した」は別の完了記録として保持する。
試作用の採用やスライス成功を、飛行可能な機体の確認済み状態へ自動で変更しない。

## 進め方

1. 原則として一つの作業単位だけを実装中にする。着手時に現状・対象・再現方法を固定する。
2. その単位の実装、意味のある回帰試験、実API・画面確認、必要な成果物確認まで行う。
3. 完了条件と証拠を記録して、小さくcommit → push → PR更新する。前からある他の作業は混ぜない。
4. 完了を確認して次へ進む。実機や外部データ待ちは未完了のまま記録し、依存しない作業だけ進められる。
5. 既存の保存・編集・PDF・動画・ZIP・キャラクターは引き継いで検証する。目的なく作り直さない。

同じ実機を使う測定や、同じ採用版からのPDF・動画の高品質生成は、必要な変更をまとめてから行う。
各修正のたびに全動画を再描画したり、モデルを取り直したりしない。
課金用の設計APIは既定無効を維持し、ローカル経路の失敗からクラウドへ自動で切り替えない。

## 各段階の具体化

### P01〜P03：整合の取れた土台

- P01ではrootの古い作業コピーを直接基準にしない。PR #48の検証済み経路と最新mainを照合し、既存の部品表・設計別出力の修正を保持する。統合操作と取り込み先を記録する。
- 既存の1.5 L・2 L案件を保存したまま開き、版とファイルハッシュを確認する。古い保存形式は移行して検査し、古い合格を黙って新形式へ流用しない。
- P02ではRequirementの要求値と、計算へ渡すDesignSpecの値の意味を先に確定する。搭載質量、目標、回収、予算、環境の変更を一つの更新として検証する。
- 判定は項目別に合格/未達/未評価を持つ。金額不明を0円にせず、予算要求が未評価なら全要求合格と表示しない。試作採用の範囲と、機体の確認済み状態を区別する。
- 不一致、古いrevision、単位違い、未入力、JSON読込み、編集後の再解析を含む回帰試験を作る。既存の数値を期待値として写すだけの試験にしない。
- P03ではWindows・Docker・WSL等の実在する経路を調べ、対応経路を明示する。UID未解決で権限を緩める解決をせず、未対応なら利用不可と対処方法を返す。
- 通常のPython/TypeScript検証は継続的に実行できる形にする。GPU、Blender/Cura、CFD等は専用の実行条件と実行記録を持ち、未実行を合格に数えない。

主な変更箇所：`rocketwright/agent/design_projects.py`、`schema.py`、`api/design_projects.py`、`DesignProduction.tsx`、`aero/openfoam_pipeline.py`、関連テストと起動文書。

### P04〜P06：候補・機材・版の共通データ

- `bottle_variables.yaml`、`bottle_literature.yaml`、ローカルの候補プール試験を、現在の`bottle_analysis.yaml`と既存カタログへ項目ごとに照合する。古いagent loopを丸ごと戻さない。
- 変数・解析手法・評価指標・組み合わせに安定したID、単位、適用範囲、依存、出典、実行可能/計画中の区別を持たせる。
- 新しい印刷信頼性の調査・skillsは、別チャットの確定成果を確認して取り込む。調査中の内容や参考値を検証済み設定にしない。
- 材料、密度・剛性等の根拠、造形方向、取付、公差を保存する。計算用の仮定値と実測値を分ける。まず手元のS5一機種を確実に扱う。
- 必要なボトル、フィン、ノーズ、取付、搭載・回収、工具等を部品表へ対応させる。未知の価格・数量は未知として残す。
- 依存関係を使って、フィン厚さ変更なら質量・空力・構造・組立・CAD・動画を失効させる。表示名だけの変更で重い解析を繰り返さない。
- 比較画面で前後の入力・要求との差・根拠・未確認を表示し、旧版も開けることを確認する。

### P07〜P08：費用をかけず、途中で戻れる設計ループ

- 既存Gemmaと既存のローカル接続を再利用する。候補プールからハーネスが適用可能な候補IDを渡し、LLMは選択と理由、要求の確認質問を返す。
- 数値、閾値、判定、実行コマンド、ファイルパスはハーネスと固定スクリプトが決める。LLMが成功を宣言しても、計算の未達を消せない。
- 対話の結果を別の見本案件へ置き換えず、その案件のDesignSpecと版へ保存する。生成中も同じジョブIDで進捗を返す。
- 欠けた条件、範囲外、矛盾、モデル不正JSON、タイムアウト、キャンセル、計算未達を実際に通す。必要な質問を一度にまとめ、既知の材料・機材を繰り返し聞かない。
- ジョブごとに入力/実装/資産ハッシュと出力先、実行所有者を保存する。API再起動後に子プロセスが残っている場合も、新しい同一ジョブを重ねて実行しない。
- GPUやスライサーのキュー、工程の完了数、動画フレーム数等から進捗を作る。残時間は計測根拠と幅を示し、根拠がなければ見込み未計測とする。
- 中断したフレームはハッシュと設定を照合して再利用し、条件が変わった出力は再利用しない。他案件や他アプリのプロセスを止めない。

### P09〜P10：階層解析の選択と変更案の採用

- 既存の`Campaign`と解析ランナーを、保存案件へ渡すアダプターを作る。旧ワークベンチと新しい保存案件で別々の正解を持たせない。
- 各解析に、要求版、形状、質量分布、材料・取付、環境、精度要求、手法版、依存結果のハッシュを記録する。
- 対象・方法・評価を、適用範囲、必要な入力、依存する証拠、利用可能な資源で絞る。候補がなければ不足条件を返し、LLMに存在しない手法を作らせない。
- 代表例の1.5 L/G10FR4の結果を、2 L/Tough PLAへコピーしない。未達、精度不足、未測定、適用範囲外を上位の結果と採用画面へ引き継ぐ。
- CFDの圧力/Cd変更案は、新しい版の候補として保存する。元案との条件差と結果差を提示し、必要な再解析後に採用して出力を切り替える。
- 適用可能な候補だけを選んだか、未達から妥当な修正へ戻れたかを、有限の検証ケースで評価する。LLMあり/規則のみの比較は同じ入力と計算予算で行う。

### P11〜P14：組立・数値検証・実物の往復

- 手・手袋・工具・治具・作業台と、工程途中の部品配置を入力にする。成人/子どもと支援者の担当は、根拠のある対象プロファイルへ対応させる。
- 最初は単純化した形状で進入/操作/離脱の干渉候補を絞り、近似と精度を表示する。必要な条件がない工程は評価済みにしない。保持、必要な力、視認と分解も別に確認する。
- 採用CADと同じ工程データから、工程別の図、必要部品・工具、操作、確認、戻し方、記録欄を作る。PDFを全ページ描画して確認する。
- P12では一つの機体を固定し、材料・取付・質量分布まで条件をそろえる。格子・領域・時間刻み・補間・独立条件を比較し、要求精度から項目別の許容差を決める。
- 既存の27.42%の格子差や高度未達を、閾値の緩和や機体のすり替えで解決しない。予算内で収束しなければ理由と次の改善を残し、その項目は未完了とする。
- 空力、熱、構造、姿勢・回収の適用条件を確認する。固定モデルの安定性定理を飛行全体の証明へ広げず、校正に使った条件とは別の条件で確認する。
- P13はまずフィン1枚、対象S5、装填材料、プレート、出力版をそろえる。前回終盤に倒れた条件を踏まえ、姿勢・接地・ブリム等の変更理由を記録し、最後まで観察する。
- 底面の初期密着だけで合格にせず、冷却後の外観・寸法・嵌合・質量・取付を記録する。失敗時は写真/動画と設定を保存し、原因候補を絞って次の試行を作る。
- P14で実測質量・寸法・取付条件を入力し直す。必要なら材料片・接合部等の測定を追加し、数値結果とのずれと不確かさを評価する。
- 実飛行をしていない段階では、その状態を残す。機体としての確認範囲を閉じるために必要な地上・飛行の確認は、実施する設備・手順・担当を定めて別の証拠として記録する。

現地で必要になるのは、プリンターの状態と初期層/終盤の確認、取外し・清掃、ノギス/はかり等の測定、取付・組立の観察。
その時点で必要な測定項目・記録用紙・写真位置を用意してから現地対応を依頼する。以前の確認を新しい試行へ無条件には流用しない。

### P15〜P17：再生成、公開、提出、最後の接続

- ZIPへ同じ版の入力、採用理由と変更履歴、部品/機材/工程、解析と限界、CAD/スライス/PDF/動画、出典/ライセンス、環境版、再生成コマンド、整合検査を収録する。
- 別環境で必要な素材・ツールが揃うか先に検査し、秘密値や個人環境のパスに依存しない形にする。必要なAI利用申告と正当な出典は保持する。
- クリーンな作業先での再生成と、実際の別PCでの確認を区別する。別PCが使えなければ、その確認を完了と書かない。
- 最新UIの配布対象を確定し、公開版で実行する機能と保存済み記録の再生を明示する。新規計算を公開する場合は、保存/アクセスの分離と資源上限も検証してから公開する。
- README、起動説明、設定、画面文言、公開URL、提出概要を同じリリース版へ揃える。
- 3分以内の日本語デモは、自然文の依頼、条件変更、失敗の発見、修正、成果物、印刷の実物という一つの体験で構成する。倍速・収録・CGを表示し、実機成功のない映像を成功例にしない。
- 提出先の確定要項を照合し、アーカイブを展開、実際の提出URLを開いて点検する。作業用の名称や生成メタデータの点検はAGENTS.mdに従い、必要な申告/著作者表示/ライセンスを保持する。共有履歴の書換え等はこの計画では行わない。
- 課金APIは最後まで無効とする。P17の直前に対象モデル、接続先、試験ケース、呼出し回数、費用上限を具体化し、その範囲だけで試験する。失敗時に無制限リトライしない。終了後は無効状態へ戻す。
- 接続試験で動作が変わった部分は回帰確認し、影響する台本・表示・動画だけ更新する。最後の提出用点検とURL確認は、その更新の後に行う。

## 一項目を閉じるときの記録

各P番号に次を記録する。テスト件数だけで項目を閉じない。

| 記録 | 必要な内容 |
| --- | --- |
| 対象 | 案件ID/版、入力・実装・機材のハッシュ、対象の要求 |
| 変更 | 以前の問題、変更した動作、影響する成果物 |
| 確認 | 実行した試験、実APIと画面、PDF/動画/ZIP等の検査、失敗と未実行 |
| 結果 | 満たした条件、残る不確かさ、再開に必要なもの |
| 同期 | commit、push、PR、統合先SHA、ローカルで残る別作業 |

## 通し試験

- **独立した二案件**：1.5 Lと2 L等、入力の異なる要求から候補・計算・CAD・PDF・映像・ZIPの由来が分かれる。
- **条件変更**：搭載質量、フィン寸法、材料/取付等を変え、必要な結果だけ失効する。旧版と新しい採用版を混ぜない。
- **未達・不足**：達成できない目標、矛盾、価格不明、適用範囲外、解析精度不足を通し、合格へ読み替えない。
- **中断と復帰**：通信断、API再起動、外部ツール失敗、キャンセルから復帰し、二重投入や他案件への影響がない。
- **成果物と実物**：同じ版のCAD寸法、印刷データ、手順書、実測、動画の説明・数値を照合する。
- **再配布**：実際に渡すZIPを展開し、案内された順に開き、可能な再生成を行い、実際の公開URLを匿名/狭幅でも確認する。

高品質動画の最終描画は、対象版が固まってから行う。途中は短い低負荷の確認と既存成果のハッシュ照合を使う。
全体の回帰試験は、共有スキーマ・依存判定・実行経路の変更と、リリース候補の節目で行う。
