# ピッチとデモで示すLLMの価値とドメイン知識

記録日: 2026-11-06

構成、スライド、話し方などの実践資料は[ピッチとプレゼンテーションの調査資料](presentation-research/2026-11-06/README.md)にまとめる。

RocketCreaterのピッチとデモでは、LLMによって初めて現実的になる利用体験、製品内部でAPIが担う役割、自分たちのドメイン知識が設計と検証に与える価値を、一つの動く流れで示す。対象オーディエンスは、Codexの学生向けハッカソンの審査員・主催者を想定する。

## 発表の中心に置くこと

CodexやLLMの能力によって、ここまでの体験を実現できると伝える。開発にCodexを使った経緯に加え、製品に組み込んだAIが、利用者のために何を理解し、判断し、操作できるようになったかを見せる。

今回の議論では、「受賞チームはすべて製品内部でAPIを使っていた」という観察が共有された。この観察と主催者の発言を踏まえ、API利用の必須・任意という形式的な条件だけで企画を判断せず、製品内部でAIが価値を生む場面を発表の中心に置く。

2026年9月15日開催の学生向けCodex開発祭について、OpenAI Japanの瀬良和弘氏は大会後の取材で、開発にCodexを使うことが当たり前になった状況を説明し、製品に組み込んだエージェントによって何が良くなるかを伝えるよう、冒頭から参加者に求めていたと述べている。[主催者への取材記事](https://realsound.jp/tech/2026/09/post-2534378.html)

この講評は上記開催回のもので、今回参加する回の正確な要項との照合は別途行う。受賞作に共通する特徴だけから、個別の採点理由までは断定しない。

## LLMによって実現する新しい体験

これまで難しかったことを、LLMによって利用者が実行できるようにする。専門知識や手作業の負担によって実用になりにくかった工程を、対話と自動処理で扱えるようにすることも含む。

API以外では技術的に絶対不可能であることまで証明する必要はない。製品内部でモデルが動くことが体験の核心になり、従来の操作や手作業から何が変わったかを示す。

企画とデモは、次の問いで確かめる。

- LLMを外すと、理解・判断・適応など、どの中心的な能力を失うか。
- 会話画面で人が一つずつ指示する場合に比べ、製品がどの作業を引き受けるか。
- ツール操作、状態管理、検証、修正が、利用者の目的に向かってつながっているか。
- 固定の処理と比較して、入力や条件の変化に応じた判断が必要か。
- その変化を、実際に動く画面と結果で確認できるか。

APIの呼び出し数やエージェント数だけで価値を説明しない。各呼び出しが利用者の成果へどう貢献するかを説明する。

## なぜ自分たちが作るのか

自分たちのドメイン知識によって、何を解くべきか、何を正解とするかを決められることを示す。知識を持っているという自己紹介に加え、その知識が製品の判断基準や検証方法をどう変えたかを具体化する。

| ドメイン知識を使う場所 | 発表で示す内容 |
| --- | --- |
| 課題の発見 | 設計のどこで迷い、どのような手戻りが起きるかを知った経験 |
| 判断基準 | 必要な制約、比較する指標、見落としやすい条件を選んだ理由 |
| 検証 | もっともらしい出力の誤りや、シミュレーションの限界を見抜く方法 |
| 成果物 | 次の作業に必要な図面・部品表・解析結果の内容と粒度 |
| 人とAIの役割 | AIに任せる判断、コードで計算する値、人が確認する事項 |

「この失敗を経験したから検証を入れた」「この条件が見落とされやすいので確認させる」という、経験と実装がつながる例を用意する。実際の研究、制作、設計、検証の記録から選び、チームの経歴や成果を作り足さない。

「なぜ自分たちしか作れないか」は、自分たちの経験が課題の選択、設計、検証にどう結び付いたかで伝える。絶対的な独占性を主張する代わりに、チーム固有の着眼点と判断を具体的な証拠で示す。

## RocketCreaterのデモで示す流れ

次の流れを、実際の実装と実行記録に照合して台本にする。

1. 利用者が自然文で要求を伝える。
2. AIが要求と制約を整理し、設計候補を考える。
3. 計算ツールが候補を検証する。
4. 問題が見つかると、AIが結果を読み、理由に沿って候補を修正する。
5. 再検証した結果と、図面・部品表などの成果物を返す。
6. 要求の一部を変えると、判断や成果物も適切に変わることを見せる。

見せ場は、条件と検証結果を受けて判断が変わるところに置く。そこで使われる制約や評価の選び方に、チームの専門的な判断がどう入っているかを説明する。

製品内部のモデル・APIと、開発に利用したCodexの役割は、実際の構成に沿ってそれぞれ示す。シミュレーション結果と実機で確認した結果も区別する。

## 台本に入れる証拠

| 伝えたいこと | 用意する証拠 |
| --- | --- |
| これまで難しかった体験が成立する | 従来の作業と、製品を使った一連の作業の比較 |
| LLMが核心的な判断を担う | 条件変更や検証結果に応じて判断が変わる実行例 |
| APIを組み込む価値がある | モデル、ツール、状態管理、成果物がつながる実演 |
| 自分たちの知識が必要だった | 経験した失敗や見落としと、それを受けて追加した設計・検証 |
| Codexによって開発を進められた | 実装、デバッグ、改善、検証に使った具体的な記録 |

## 台本作成前に埋める項目

- 想定ユーザーと、実際に困っている一つの作業。
- チーム固有の経験・研究・制作記録から選ぶ具体例。
- ドメイン知識によって追加・変更した制約や検証の例。
- 実演する条件変更と、それに対して期待する判断の変化。
- 通常のチャットや固定処理と比較する条件と評価指標。
- 実際に使っているモデル・API・Codexの役割と、その裏付け。

改善率や所要時間は、比較条件をそろえて測定してから記載する。未実装の流れは将来案として扱う。
