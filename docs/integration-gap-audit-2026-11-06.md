# 統合版の不足事項と完成条件

確認日：2026-11-06。コードの基準は `main` の `08d026db85d27440bd45ef11758443d525a0fd78`。
これは開発状況の整理であり、最終提出前チェックの完了記録ではない。

## 結論

設計・解析・CAD・スライス・動画・PDFの部品は多くそろっている。
一番大きな不足は、**利用者が新しく依頼した一つの設計を、同じ版・形状・条件のまま、解析、修正、製作資料、印刷データ、動画まで通すこと**。
特定の保存済み設計で動いた機能と、現在の自由設計画面から使える機能を分ける必要がある。

## 完成したと判断する条件

### まず一本を通す：G01〜G04

1. 現行画面で新規のペトロケ要求を入力し、既存Gemmaで要求整理と候補提案を行う。数値・合否は計算コードが決める。課金API無効のまま完走する。
2. 実測値と仮定値を識別した設計レコードを作る。形状・材料・部品・質量・要求・環境・解析版の識別子を持ち、形状を変えたときに古い合格結果を持ち越さない。
3. 同じレコードからレポート、CAD、S5スライス、組立工程、動画を出す。既存の1.5 L/2 L例を無言で代入しない。条件不足の成果物は未生成の理由を返す。
4. Gemmaの動画提案は登録済み部位・カメラ等に制限し、寸法・軌跡・字幕の数値は確定データから作る。制作中・失敗・再開の画面を通して、生成した2本を保存できる。
5. 組立手順PDFは同じ部品表・工程・図版から生成し、全ページをレンダリングして文字・図・寸法・対象版を目視確認する。製作票を手順書として扱わない。

この通し試験には、独立した二つの要求と途中の条件変更を使う。設計ID・寸法・部品・数値・ファイルの由来が変わり、旧成果物との混同が起きないことを確認する。
課金APIの接続はユーザーの方針どおり最後の限定試験に残す。

### 実機で確かめる：G05

次のフィンは生成済みで、再印刷成功の記録はない。
[次のフィン1枚分](../assets/print-trials/next-fin-s5/README.md)は、以前の形状に20 mm・隙間0の除去ブリムを付けたS5専用データ。
推定約114分・16.49 gは実測ではない。

- 初層だけでなく、前回倒れた終盤を含めて完了まで観察・撮影する。
- 冷却後の品質・寸法・ボトルへの嵌合を確認し、除去後の部品質量を測る。
- 取付方法と強度の根拠を確認し、部品の置換を飛行・回収・安定性の入力へ戻す。
- 本体の100%やG-code検査合格では、`physical_print_verified` を真にしない。

実機を使う操作はこの整理作業では行っていない。

### 継続利用と整合性：G06〜G11

- 保存案件を開き直しても、採用版、計算条件、履歴、出力、未確認事項が復元できる。API再起動後にも登録済み成果物を取得できる。
- フィン寸法・材料・機材条件の変更について、依存する計算と手順を失効させ、再検証後にだけ新しい版へ採用する。
- 一括ZIPを展開し、目録のハッシュ・参照・版を同梱スクリプトで検査する。検査合格と機体の性能・実機合格を分ける。
- 手や工具の干渉は実寸データで評価し、装飾キャラクターの大きさで代用しない。
- キャラクターは待機・点検・片付けで動作そのものを変える。現在の停止・動作軽減・非表示と、計算状態への非干渉を維持する。

コード読取で追加の照合対象も見つかった。`page.tsx` の部品表CSVは対象設計の出力がないと別の出力へフォールバックし、条件別試行も対象IDにないと直近結果へフォールバックする。
複数案を切り替えたときに異なる設計の資料・結果を表示しないか、再現試験が必要。今回の整理では実際の誤表示までは再現していない。

### 解析例の未達を残す：G09

[具体材料案](../scenarios/concrete_fin/RESULTS.md)の19.3〜19.7 mと格子差27.42%は、そのケースの未達を示す。
全てのペトロケ設計が同じ結果になるという意味ではない。
G10FR4の材料値・継手許容値、ボルト接触・滑り等も未確認で、温間FEMのメッシュ比較合格だけで実機を認定できない。
LaSalleの固定モデル76点の成立は、非線形飛行全体の安定性を保証しない。
WindowsのOpenFOAM呼出しには `os.getuid()` による既知の失敗が記録されており、対応バックエンドと実行環境の確認が必要。

一般的な階層最適化、探索空間自体の共同設計、任意機種対応、月到達は将来範囲。今回のペトロケの通し完成条件へ混ぜない。

## 実装不足として数えないもの

- Gemmaの導入：既存モデルと接続を再利用できる。新しい小型モデルの取得は不要。
- 写真調映像の基礎：凍結した1.5 L設計から新しく生成した16秒/12秒のCGは[実生成証拠](../assets/product-demo/current-design/README.md)がある。G03は現行UIと任意新規案件への接続の不足。
- 印刷生成処理：新しい形状のBlender/Cura生成と検査の記録がある。G02/G05は代表寸法、解析との一致、実機成功の不足。
- PDF：製作票と既定設計の組立手順書は存在する。G04は自由設計の工程生成と画面接続の不足。
- 文献：水ロケット98件・モデルロケット81件の索引はある。資料数の追加より、判断に使った出典と適用範囲を新規案件へ記録することを優先する。
- 印刷経過の動画：終盤転倒を含む[公称200倍速動画](../assets/print-trials/2026-11-06-fin-retry02/README.md)は保存済み。成功動画はまだない。

## 公開・提出の不足：G12

[公開された機能デモ](https://rocketwright-ui-demo.taichi-uchida-offici.chatgpt.site/functional/)は、PR #37の記録上、保存済みの工程と成果物を操作するもの。

2 Lの参照映像の本体はローカル素材ディレクトリを使うため、新しいPCでGitを取得するだけで全映像を再生できるとは扱わない。

提出用には、以下が未完了。

1. 対象大会と提出フォームを基準に、台本・配点・必須項目をそろえる。元の参加者ガイドを扱うチャットはBuilt with Claude: Japan 2026を記録しているが、ピッチ方針・制作ワークシートは学生向けCodex大会を想定している。別イベントの講評を今回の要項と同一視しない。
2. 3分以内の最終動画、閲覧可能なURL、概要文、AIの役割の説明を確定する。調査資料・短いCG・失敗タイムラプスは最終デモ動画そのものではない。
3. 「入力→AIの判断→計算で問題発見→修正→成果物」を最新画面で実演し、実行記録を添える。ライブと記録再生、CGと実機を表示で識別する。
4. 提出範囲を確定してからAGENTS.mdの最終提出前チェックを行う。ファイル・URL・リポジトリの作業用名称とメタデータ、素材のライセンス・出典・必要なAI利用申告を確認する。現時点でチェック完了とはしない。
